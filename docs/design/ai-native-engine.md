## 问题定义

2026 年的基线已经不是「聊天框生成代码」。Unity AI、Roblox Assistant 与 GDevelop AI 都能读取项目并直接修改编辑器状态；
Roblox 还交付了可编辑计划、批准门、checkpoint、虚拟输入试玩与自动修复。

因此 **AI 通道内生**仍是 Clay 的必要结构，但不再足以单独构成差异。真正的问题变成：

> **模型改了什么能否逐步证明，错误判通过时谁能拦住，失败后能否无污染地回到最后一个已知正确状态。**

下面五根支柱提供感知、能力、行动、结构反馈与确定性运行；v20 的验证控制协议负责把它们组成
可批准、可提交、可判定、可停止的产品闭环；v21 的证据演化协议负责在计划之前发现隐含决策，
并让当前方案在不改变产品意图的前提下被更强证据取代。

## 支柱一 · 单一变更通道

**规则：编辑期世界状态只能通过 Action 改变。** 鼠标、AI、事件表编辑、读档全部收敛到同一入口。

```
场景 = 初始状态 + Action 序列
```

这是**语义模型**，用于 diff、回放、审计；**不是存储实现**（见[明确不做](#本文范围内明确不做)）。

白送的能力：

| 能力 | 为什么白送 |
|---|---|
| AI 的每一步都能被人单独撤销 | 和人的操作在同一个栈里 |
| diff 的是**意图**不是**结果** | 「改了 3 个坐标」→「把这条路的半径从 8 改成 25」 |
| 完整操作回放 / 教学录像 | 日志就是录像 |
| AI 行为完全可审计 | 每一步留痕、带参数 |

**现状**：[History](../../js/core/History.js) + 17 个 Command 已经是这根支柱的九成。
差的是**「唯一入口」的强制**——迁移到 ECS 内核时补上，晚补一天就多一天旁路债。

## 支柱二 · Action Registry 与渐进披露

每个 Action 声明自己的元信息：

```js
{
  id: 'unit.spawn',
  params: { /* JSON Schema，见下方子集约束 */ },
  preconditions: [...],          // 什么情况下可用
  affects: ['transform', 'ai'],  // 影响域
  reversible: true,
  describe: (params) => '在出生点生成 3 个近战单位',
}
```

### 关键：不要一个 Action 一个 tool

2026 的 agent 工程共识是**渐进披露**——预加载全量工具目录是上下文浪费的最大单一来源
（Unity MCP 一家就 268 个工具；多个 server 并存时开场即烧数万 token）。
Action 会随模块持续增长，全量暴露必然失控。

**对模型只暴露三个稳定入口**：

```js
describe(scope, detail)          // 看世界（支柱三）
listAvailableActions(context)    // 此刻能做什么，按需返回 schema
apply(actions[])                 // 执行，返回约束校验结果（支柱四）
```

`listAvailableActions` 是**情境级自省**——不是「这个类有哪些方法」，而是
「当前选中这个物体、处于这个模式，什么操作有意义、影响谁、能不能撤销」。
Action 加到 500 个，上下文成本也不涨。

同一份 registry 白送：命令面板（Ctrl+P）、宏录制、脚本控制台、测试夹具、快捷键系统——
以及**任何能力过滤视图**（goals.md **I8**）：过滤是 registry 的一个视图，不是第二套代码。
（goals.md 决策 12 的双模式已于 v17 取消，**但这个机制留着**：日后要做面向新手的裁剪界面，入口在这里。）

### params 的 JSON Schema 子集约束（硬性）

Action 的 params schema **必须能原样喂给模型做约束解码**。因此禁止：

- 自定义类型、引擎内部类的引用
- 深嵌套 `oneOf` / `anyOf`（一层以内）
- 运行时求值的默认值
- 靠文档描述、schema 里表达不出的隐含契约

理由：约束解码把**语法错误压到零**，约束层的重试预算全部留给**语义错误**。
这条不早定，17 个命令各写各的 schema，等接模型时会有一半不可用。

### 三个入口就是能力降级的边界（I10）

供应商适配层、能力探测、降级矩阵、设置界面**全部写在 goals.md §5.5**，本文不重复。
这里只补一句实现上的要点：

> **降级发生在这三个入口内部，不外溢。** 没有约束解码就「贴 schema + 校验 + 带结构化原因重试」，
> 没有工具调用就把三个入口退化成单轮 JSON 协议——**上层的 Action 序列与约束层完全不受影响**。

**禁止**：在提示词、协议或解析里依赖任何一家的独有字段与行为。判据是闸门 D.6。

## 支柱三 · describe：语义 LOD

每个状态子系统实现两个接口：

```js
serialize()                 // 精确、稠密、给机器（已有）
describe(scope, detail)     // 语义、稀疏、给 AI 和界面（缺）
```

**语义描述必须可寻址、可下钻**——先看全局摘要，锁定感兴趣区域再要细节：

```js
terrain.describe({ at: [120, 80], radius: 20 }, 'detailed')
```

这与支柱二的渐进披露是**同一个机制的两个面**（结构 vs 能力），不要做成两套 API。

### describe 返回结构化数据，不返回文案

反面例子是让引擎生成「西南缓坡、最陡 8%、中部有东西向走廊」这样的句子——
那是**模型该做的事**，写进引擎就是把生成成本和语言维护搬进内核，还要乘以 i18n。

引擎输出的是分区统计、极值、坡度直方图、标注区域、拓扑关系。
[ui/outliner.js](../../js/ui/outliner.js) 与 [ui/details.js](../../js/ui/details.js) 是这件事的人类版本，
应与 AI 版本共用同一份数据源，避免人机两套描述慢慢跑偏。

**优先级：地形最先做。** 它是目前唯一让 AI 完全失明的子系统——
`heights: Float32Array` 在 1024×1024 下是一百万个数，读不动也写不动。

## 支柱四 · 约束层：结构化的失败反馈

有效状态的判据不能是「运行时崩不崩」——那个信号又慢又稀疏，而绝大多数错误根本不崩，只是不对。
约束层把「什么是有效」变成一组可枚举、可解释的谓词。

```js
{
  id: 'road.maxGrade',
  severity: 'error' | 'warning',
  check: (world) => [
    {
      at: { entity: 42, segment: 3 },   // 位置
      observed: 0.11,                    // 实测值
      limit: 0.08,                       // 约束值
      alternatives: [                    // 可行替代 —— suggest 由它生成
        { action: 'road.adjustProfile', params: { grade: 0.08 } },
      ],
      message: '这段路坡度 11%，超过卡车爬坡上限 8%',   // 只用于渲染给人看
    },
  ],
}
```

### `at / observed / limit / alternatives` 四元组是硬要求

修复环的实证结论一致：**给出位置 + 实测值 + 可行替代**的反馈，
其修复收敛速度显著优于原始诊断信息；只给位置而不给替代不够。
这决定了 AI 重试是收敛还是乱撞，而字段成本几乎为零。

**第一批约束里必须有一条「皮肤包完整性」**（goals.md 决策 20）：
当前皮肤是否覆盖了事件表用到的每个 kind 与动画状态。
它是 I9 的执行点，也是 AI 换皮后自检的依据——缺什么，`alternatives` 里直接给出补哪个插槽。

一份约束集同时喂五个消费者：

1. **AI 的验证器**——生成后自动校验，失败带结构化原因回炉
2. **AI 的搜索信号**——从二值信号升级为密集、可解释的评分
3. **人的实时反馈**——现在 [tools/RoadTool.js](../../js/tools/RoadTool.js) 的红色禁建提示是硬编码的；抽出来后所有工具白送（goals.md §3.4「错误必须便宜」）
4. **测试**——约束就是断言，现有 16 个套件有相当一部分可改写成约束
5. **文档**——约束集就是「这个引擎的世界规则」的可执行说明书

## 支柱五 · Headless 与确定性

两个要求：

- **无渲染可跑**——已做到（数据层零 three.js 依赖，本项目最大的存量资产）
- **确定性**——相同 Action 序列必然产生相同状态。**这是硬要求，不允许降级**（goals.md 决策 29），
  因为 lockstep 联机以它为前提；断言范围限定在**玩法状态**，不含渲染与视听。
  **执行点是 goals.md §7.1 的确定性沙箱**：条件与动作的 JS 实现禁触时间与随机源，
  由内核注入 `rng`、`tick` 与 `dt`，注册时静态检查（[adr-002](adr-002-eventsheet-eval.md) §8）
- **事件顺序也是确定性的一部分**（r2 新增 D4）——同一物理步内产生的触发事件，
  入队前按 `(类型, 主实体 id, 次实体 id)` 稳定排序。物理引擎交回的原始顺序**不保证跨平台一致**，
  而顺序不同就足以让世界状态分叉。**这一条是[真推演](adr-002-walkthrough.md)撞出来的，纸面通读四个版本都没发现**

第二条**尚未做到**：[GameClock](../../js/sim/GameClock.js) 用 `new Date()` 初始化，
[core/project.js](../../js/core/project.js) 用 `randomUUID()`。
非确定性一旦渗进世界状态，回放和 A/B 试算全废。改由 Action 参数传入即可。

做到后解锁两件事：

1. **AI 在沙箱里跑 N 个方案变体，用约束层打分，只把最好的提交给人审阅。** 从「生成一个答案」变成「搜索解空间」。
   **这与五根支柱合起来就是 agent 的完整闭环**——感知（支柱三）· 知道能做什么（支柱二）·
   行动（支柱一）· 获得结构反馈（支柱四）· 重放成果（支柱五）。goals.md 决策 40 把它写成了可分档的能力。
   **五根支柱不用重做，但必须补计划、事务、oracle、证据与停止语义。**
2. **脚本化试玩 + 断言**——这件事**不需要 AI**，是纯试飞台能力，
   它是**闸门 C.3「1000 单位规模下由脚本跑完并断言」**的直接依赖。
   同类能力已在商业平台落地（Roblox Assistant 的自动试玩，2026-04）。**早做早受益。**

## 控制协议 · Plan-Build-Verify-Repair

完整字段与状态语义以 [ADR-003](adr-003-verified-agent-loop.md) 为准。这里说明它怎样接到五根支柱上：

```text
用户意图
  → planner 生成 PlanContract（describe + listAvailableActions）
  → 人批准具体 plan version 与 baseRevision
  → orchestrator 在候选事务执行一步（apply）
  → verifier 跑 V1 结构 / V2 行为 / V3 体验证据
  → hard oracle 全过：commit checkpoint
  → 未通过：带失败签名进入有界 repair，或停止交还用户
```

| 控制对象 | 引擎负责 | 模型负责 |
|---|---|---|
| 计划 | schema、版本、作用域、审批失效 | 目标拆解、假设、步骤与 TestSpec 建议 |
| 执行 | `baseRevision`、事务、幂等、权限、真实 `affects` | 提议符合本步白名单的 Action |
| 验证 | 运行 TestSpec、hard / soft 边界、最终判定 | 解释观测、提出体验问题 |
| 修复 | 预算、重复失败检测、禁止改 hard 测试、停止 | 原因假设与最小修复 Action |
| 证据 | `StepReceipt`、`EvidenceLedger`、重放 | 给人看的摘要 |

### 三层验证不是三票表决

- **V1 结构**：schema、前置条件、引用完整性与约束层。失败即失败。
- **V2 行为**：固定 seed、输入意图轨迹、状态断言与回归测试。hard oracle 的主要来源。
- **V3 体验**：日志、截图、真实键鼠和视觉判断。默认是 soft 证据，不能覆盖 V1 / V2。

直接传送角色只能验证某个目标状态可达，不能验证真实输入、相机、导航或角色控制器。
测试这些系统时，TestSpec 必须声明输入意图轨迹，禁止用更短的旁路让测试“通过”。

### 隔离的是权限与上下文，不强制多模型

planner 只读，executor 才能提出 `apply`，verifier 只能运行已批准的 TestSpec 与读取候选 diff。
三者可以由同一个 provider / model 顺序承担，但上下文必须隔离；verifier 不接收 executor 的自我结论。
运行状态属于引擎的 `Run`，三个入口继续无状态，provider 会话不是恢复依据。

### 修复必须收敛或停止

每轮修复先提交失败签名、原因假设、最小 Action 集和回归范围。同一失败连续两次、影响域越界、
试图削弱 hard TestSpec、缺少 registry 原语、revision 冲突或任一预算耗尽，立即停止到 `NeedsReview`。
停止时交付最后通过的 checkpoint 与完整证据，而不是继续碰运气。

## 研发治理 · Discover-Challenge-Evolve

完整协议以 [ADR-004](adr-004-evidence-governed-evolution.md) 为准。它位于 `PlanContract` 之前，
约束的是开发 Clay 的 AI 以及未来设计代理，不是运行期游戏 AI：

```text
用户意图 / goals 不变量
  → TaskContract（事实、假设、scope、权限）
  → 十二面 DecisionCoverage + 负空间扫描
  → U-NNN / DecisionChallenge / 可逆实验
  → 证据足够后生成 PlanContract
  → ADR-003 执行与验证
  → evidence package 更新 champion 或保留现状
```

| 控制对象 | 系统负责 | AI 负责 |
|---|---|---|
| 决策覆盖 | 十二面状态不可留空，`open` 必须链接 `U-NNN` | 主动寻找用户未提出的语义、边界和反例 |
| 风险路由 | 按不可逆性 × 不确定性 × 影响面限制提交范围 | 提议最小可逆 probe 和仍可继续的工作 |
| 决策挑战 | 保护意图、hard oracle、权限与历史；要求明确批准 | 给出隐含决策、选项、证据和推荐，不替用户做产品取舍 |
| 方案演化 | 保留 champion、同一 hard criteria、shadow、迁移与回退 | 生成 challenger，解释收益和退化轴 |
| 机制演化 | 历史漏判集 + 新植入案例；测遗漏召回和无效挑战负担 | 提议增删检查项，但必须指出捕获的失败模式 |

**同一模型可以参与多个环节，裁决不能复用同一上下文的自我结论。** 关键未知至少需要隔离 skeptic
和一种异质证据（参考实现、官方来源、第二实现、另一 provider 或领域专家）。多个模型同意不是证据。

## 事件表的生成方式

goals.md 决策 13 把逻辑层定为**事件表**（有序的「当……就……」规则行），
其中一半理由就是 AI 侧的：**模型写有序列表远比写图可靠**。
图结构生成需要空间推理与多步规划，是当前模型的公认短板（如 GVGAI-LLM 的 118 游戏 zero-shot 评测），
而且整图直吐的失败是**整体失败**，无法定位。

即便如此，**仍然不要让模型一次吐出整张表**。**改为吐 Action 序列**：

```
rule.add / rule.addCondition / rule.addEffect / rule.setParam / rule.move
```

每一步过约束、可撤销、可局部失败，**失败点能精确到第几条规则的第几行**。
这同时让 goals.md 的 I1 与 I3 自动成立——AI 写规则和人写规则**走的是同一条路径**。

**优先挑配方，再填参**：配方 = **一个行为单元 + 一组默认参数 + 一句说明**（goals.md §4.3）。
模型的首选动作是挑一个配方、填参数，只有都不合适才逐行拼，最后才定义新的行为单元。
展开后就是普通规则行——**AI 走的和人走的是同一条路径**。

**措辞由注册方提供，不由模型即时生成**：每个条件与动作在注册时自带人话模板串
（`当 {对象} 进入 {目标} 的范围`）。理由是 I3——
措辞每次显示都不一样，用户就无法确认「这和我上次改的是同一个东西」，
「同一种材料」这条就松了。代价是每个条件动作要写一句文案，这笔成本是值的。

**顺带的好处**：事件表是有序行，AI 的产出可以**逐行 diff 后再呈现给用户**——
「新增了第 4–6 行，修改了第 2 行的这个参数」。节点图给不出这种粒度的变更说明。

## AI 介入形态

按信任成本从低到高，也是实现顺序：

| 形态 | 评价 |
|---|---|
| **决策挑战** | 计划前发现未决语义、越权或证据冲突时，生成结构化 `DecisionChallenge`；只暂停相关不可逆提交，无关工作继续 |
| **单步指令** | **起点。** 一句话 → 一条 Action → 预览 → 确认。作用域小、错了代价低、用户能立刻判断对错。**应在内核地基完成时就接**——验证的是通道形状，不是模型能力，早发现比晚发现便宜一个数量级 |
| **内联建议** | 选中物体 → 详情面板给 1–2 条建议（「路口半径 8m，重卡过不去，改 25m？」）→ 点一下变成一条标准 Action |
| **多步变更集** | N 条 Action → 视口半透明预览 + 清单 → 整体接受 / 逐条剔除 → 接受后合成一条撤销记录 |
| **生成规则行** | 走上一节的 Action 序列路径，产出可见、可手改、可逐行 diff 的规则 |
| **换皮 / 配皮肤** | 「换成赛博朋克风」→ 只改皮肤包映射，**不碰任何规则**（I9）。作用域极小、错了一眼看得出，是 AI 最安全的一类任务 |
| **验证驱动的自主循环** | **本轮做**（goals.md 决策 40 的 v20 修订）。`PlanContract` 经批准后逐步执行 Action 事务，每步经三层验证；通过才提交 checkpoint，失败进入有界修复并写入 `EvidenceLedger`。与一次性多步变更集的差别是**控制权与持久运行状态**，不是任务规模 |
| **AI 造零件** | **留口**（档 3）。AI 用 JS 实现新的条件与动作。**不得自动注册**：必须过确定性沙箱静态检查 + headless 断言，并在 registry 标明来源（I11） |
| 产出黑盒结果 | **不做。** 不可寻址、不可手改、改一处要重来——与 I3 直接冲突。**注意封的是形态不是规模**：任务多大都行，产出必须始终是 Action 序列 |

### AI 在 v17 之后的位置（goals.md 决策 35）

原文这里是一张「简易模式 vs 专业模式」的对照表。**双模式已于 v17 取消**，
但更重要的变化是 AI 的**分量**：

> **决策 35 把门槛交给了 AI 与内置教程，于是 AI 从「产品卖点」变成「承重结构」。**

| | 含义 |
|---|---|
| **位置** | 与直接操作并列的主要修改方式，**同时是「我不知道怎么做」的答案** |
| **主用形态** | 单步指令、挑配方并填参（低信任成本）→ 多步变更集、逐行改规则（高） |
| **失败时** | **必须能退回到「用模板 + 配方 + 教程手动做」**。这条从「兜底」升为硬要求——AI 挂了门槛就没人承担 |

**共用的是同一套 Action 与同一份 registry。** 任何视图只改变暴露面与文案，不改变通道（I8）。

### 非功能项（与功能同等对待）

- **延迟**：慢到十几秒，「省下手工操作」的价值就没了
- **预算**：按任务记录时间、Action 数、修复轮数与费用；模型不能自行延长
- **错误通过率**：闸门 D 的人工植入 hard 负例必须 0 错误通过
- **失败兜底**：AI 不可用 / 超时 / 乱答时，编辑器必须完全可用
- **可解释**：每次变更都要能说清「改了什么、为什么」
- **可恢复**：失败步骤不污染主工程，回到最近通过 checkpoint 的 Action 距离恒为 0
- **离线**：没有 AI 也能用模板与条件动作库做事
- **供应商无关**：能力探测 + 降级矩阵见上文「模型无关层」；用户可填自己的端点与模型（决策 21）

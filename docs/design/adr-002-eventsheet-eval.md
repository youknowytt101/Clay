## 1. 为什么这一份要单独写，而且要最早写

[goals.md](goals.md) §3.6.5 的原话：

> **真正需要冻结的不是渲染层，是事件表的求值语义。**
> 改实现（换 ECS 库 / 换渲染器 / 换物理 / 换宿主）→ 作品留得下来；
> 改求值语义 → **迁移链救不了**：作品还能打开，但跑出来的行为变了。

这是全项目**唯一一处「定错了没有退路」**的地方。原计划把它排在阶段二，
而阶段零到阶段二之间会先落地 Action 层、内核、序列化——**它们的形状全部受这份语义约束**。
排在后面等于让最不可逆的决策去迁就已经写好的代码。

**因此决策 31：本文前置到阶段零，与打包器同期定稿。**

## 2. 要回答的五个问题

不是「事件表长什么样」（决策 13 已定），是**它每一帧到底怎么跑**：

| # | 问题 | 定错了会怎样 |
|---|---|---|
| Q1 | **求值模型**：每帧全表 / 纯事件驱动 / 混合 | 规则的执行时机变，所有作品行为漂移 |
| Q2 | **实体集传递**：规则行之间「被选中的实体」怎么流动 | 同一张表在两种语义下跑出完全不同的结果 |
| Q3 | **空集与取反** | 最高频的一类静默错误 |
| Q4 | **动作的可见性**：后面的条件看不看得到前面动作的结果 | 顺序敏感性不确定，用户无法预测 |
| Q5 | **等待 / 延时的续延** | 存档与确定性同时漂 |

## 3. Q1 · 求值模型

| 候选 | 优点 | 致命处 |
|---|---|---|
| **纯每帧全表** | 语义最简单、最可预测 | 「被点击」「碰撞发生」这类**瞬时事件**表达不了，只能靠标志位轮询，用户读不懂（破 I2） |
| **纯事件驱动** | 性能好 | 「每帧检查血量是否 < 0」这类**持续条件**要用户自己想办法造事件，门槛陡升 |
| **混合**（选定） | 两类条件各归其位，与用户直觉一致 | 两条路径的**交错顺序**必须写死，否则确定性没了 |

### 决策

> **固定步长下自上而下全表求值（常规规则）+ 触发型规则由事件即时插入（触发规则）。**

这是 Construct / GDevelop 被十几年实践验证过的模型（[goals.md A.2](goals.md#a2-决策-13为什么是事件表不是节点图)），
不另发明。**每个条件在注册时声明自己是「常规」还是「触发」**，界面上用不同图标区分。

### 交错顺序（确定性的执行点）

一个 tick 内严格按此顺序，**不允许并发、不允许乱序**：

```
tick 开始
  1. 采样输入意图（I12），冻结本 tick 的输入快照
  2. 物理步进（Rapier，固定步长）
  2.5 收集本 step 产生的全部触发事件，按 D4 稳定排序后入队   ← r2 新增
  3. 排空触发队列：按入队顺序 FIFO，逐个执行其规则分支
       —— 执行中新产生的触发继续入队，本 tick 内排空
       —— 排空深度上限 N（默认 16），超限记 warning 并丢弃，不静默死循环
  4. 全表自上而下求值常规规则
  5. 结算等待队列与计时器（见 Q5、§7.2）
tick 结束
```

> **step 2.5 是 r2 新增的，它不是实现细节。** 没有它，"按入队顺序 FIFO"里的"入队顺序"
> 由物理引擎内部的遍历顺序决定，**跨平台不保证一致** → 直接击穿决策 29。见 [§8 的 D4](#8-确定性的三条附加约束)。

### 3.3 触发规则的初始集合（r2 新增 · A1）

> **触发规则的初始集合 = 触发载荷涉及的实体。**
> 被载荷提及的每个种类为**单元素集**；**未被载荷提及的种类仍从全集开始**（§4）。

原文 §3 说触发"逐个执行其规则分支"，§4 说"每条顶层规则从全集开始"——
**两句各自读都成立，合起来推演就撞车**：若触发规则真从全集开始，
任意一对实体进入范围会让**所有**满足条件的实体执行动作。

**输入意图类触发不携带实体载荷**（`意图「跳跃」被按下`），其规则的所有种类均从全集开始。
要绑定到具体角色，须写显式条件（如 `角色 是本地玩家`）——
**否则分屏 / 联机下所有角色会一起响应**。

### 3.4 四条硬性质

| # | 性质 | 理由 |
|---|---|---|
| **E1** | 触发**先于**全表求值 | 「碰到就扣血」要在「血量 < 0 就死亡」之前，否则死亡延迟一帧 |
| **E2** | 触发在 **tick 边界对齐**，不在物理子步内立即回调 | 物理回调里改世界会破坏 Rapier 的确定性与快照一致性 |
| **E3** | 排空有**深度上限**，超限是 warning 不是崩溃 | §3.4 封了递归与任意控制流，但触发链可以间接成环 |
| **E4**<br>（r2） | 排空时若**载荷实体已销毁 → 跳过该事件**，不报错、不中止后续事件 | 前一个事件的动作可以销毁后一个事件的载荷（Q4 动作立即写世界）。与 **W3** 对等待队列的处理对齐 |

## 4. Q2 · 实体集传递（picking）

**这是全文最容易定错的一条**，也是同一张表在两种语义下跑出不同结果的根源。

### 决策

```
每条顶层规则从「全集」开始
  → 每个条件在当前集合上做筛选，逐个收窄（多条件 = 交集 AND）
  → 动作对收窄后的集合「逐个」执行
  → 子事件继承父事件收窄后的集合，继续收窄
  → 规则结束，集合丢弃；下一条顶层规则重新从全集开始
```

三条硬性质：

| # | 性质 | 反例（定错的样子） |
|---|---|---|
| **P1** | 收窄是**按种类**的：条件筛选「敌人」不影响「塔」的当前集合 | 若做成全局单一集合，两个种类的条件会互相污染 |
| **P2** | **子事件只继承，不回写**：子事件里的收窄不影响兄弟子事件 | 若回写，规则的阅读顺序与执行结果脱钩，用户读不懂（破 I2） |
| **P3** | 顶层规则之间**不传递** | 若传递，插入一条新规则会改变它下面所有规则的行为——AI 逐行 diff 的前提就没了 |

**P3 是与「AI 产出可逐行 diff」（[A.2](goals.md#a2-决策-13为什么是事件表不是节点图)）直接咬合的一条**：
只有规则之间互不干涉，「新增了第 4–6 行」才是一个安全的说法。

### 4.1 关联查询原语族（r2 新增 · B3′）

上面的模型是**单调收窄**：集合只会变小，且各种类互不影响（P1）。
但「**每座塔各打自己射程内最近的敌人**」需要的不是收窄，是**配对**——
对每个塔，在与它相关的敌人子集里选一个。单调收窄模型推不出这个结果。

> **求值模型中唯一允许「看到当前集合之外实体」的构造，是一族参数化的关联查询条件：**
>
> ```
> <A> 的 <关系> 中 <排序> 最优的 <B>
> ```
>
> - **关系**：范围内 / 拥有的 / 携带的 / 目标是 …… **可扩展注册**
> - **排序**：最近 / 最远 / 属性最大 / 属性最小 / 角度最小 …… **可扩展注册**

**语义**：对当前 A 集合的每个实例 `a`，在 `a` 的关系集合内按排序取最优的一个 `b`，
形成配对 `(a, b)`；随后 **A 收窄为有配对的 a**，**B 收窄为被选中的 b 的并集**；
本条规则内后续的动作按**配对**逐个执行，而不是按笛卡尔积。

三条约束：

| # | 约束 | 理由 |
|---|---|---|
| **R1** | 配对状态**只在本条顶层规则内存活**，规则结束即丢弃 | 与 **P3** 一致。否则插入一条规则会改变下面所有规则的行为，逐行 diff 的前提失效 |
| **R2** | **不允许嵌套关联查询**（一条规则内只能有一层配对） | 两层配对的语义（作用域生命周期、回写、与 P2 的交互）**没有推演过**，不在冻结范围内 |
| **R3** | 关系与排序都必须是**注册项**，不接受任意表达式 | 任意表达式会把求值语义变成通用查询语言，那是不可逆的扩张 |
| **R4**<br>（r2 第二轮） | 配对在**条件阶段一次性建立**；动作按配对逐个执行时，**任一端已销毁 → 跳过该配对** | 配对是快照，而动作立即写世界（Q4）：`T1` 开火可以杀死 `T2` 那一对里的敌人。**与 E4、W3 同构** |

> **R4 是同一个模式第三次出现**：W3（等待队列的实体快照）、E4（触发队列的载荷）、
> R4（关联查询的配对）——三处都是"**被快照的实体引用，在使用时可能已经失效**"。
> 三条语义完全一致：**跳过，不报错，不中止其余项**。
> 冻结后若要统一成一条通则，属于表述重构而非语义变更。

#### 为什么是原语族，不是通用作用域

另一条路（**B2**）是直接改本节的模型，引入通用关联作用域：动作逐个执行时为当前实例建作用域，
其他种类在该作用域内重新求值。**它的表达力严格更强**，两层以上的嵌套关联也能写。

不选它，理由**不是**「原语更简单」——而是**证据时序**：

> 关联查询到底有多少种模式，是个**经验问题**，答案要等 M2 真写 RTS 模板才有。
> 而本文必须在 M0 冻结，**证据到不了**。
>
> B2 要改的是求值语义主体，**冻结后不可逆**；而作用域的生命周期、嵌套语义、能否回写父集合、
> 与 P2/P3 如何交互——**现在一条都没推演过**。
> **那等于拿全项目最贵的容器，去装最不确定的东西。**
>
> 原语族则相反：单个原语的语义可以冻结，**原语集合可以增长**——加错一个可以废弃，
> 旧作品仍按旧原语的语义跑。**不确定的部分放进可逆的容器。**

**已知代价（写出来，不藏着）**：R2 封死了两层以上的关联
（「对每个塔，对它范围内每个敌人，再查该敌人的护盾来源」这类写不出来）。
判断是八款目标游戏里这类需求很少，**但这是假设不是事实**——
它的失效信号已登记为 [`U-034`](goals.md#九--未决项)：
**M2 真写 RTS 模板时若出现两层关联需求，重开 B2 / B3′ 的比较。**

## 5. Q3 · 空集与取反

| 情形 | 语义 | 理由 |
|---|---|---|
| 条件筛出**空集** | 该规则的动作与全部子事件**不执行** | 唯一符合直觉的选择。反面（空集视为「对全体执行」）是灾难 |
| **取反条件**（「没有敌人在范围内」） | **只做布尔判定，不改变当前集合** | 取反本来就选不出实体；若让它清空集合，后续动作全部哑火 |
| 无种类的纯布尔条件（「金钱 > 100」） | 同上，不改变集合 | 同上 |
| **「存在 X」形式**（「存在 被选中的单位」）<br>（r2） | **就是普通筛选条件**，不是独立形态。其「存在」语义由上面第一行的空集规则**自动获得** | 若做成布尔判定不收窄，`被选中的单位 移动到 光标位置` 会对**全集**执行——**所有单位都移动** |

界面上取反条件必须有**视觉区分**（不同底色 + 前缀词），否则用户会以为它和普通条件一样参与筛选。

> **「存在 X」这条必须写明，不能靠实现者自行判断。** 它的错误形态在测试里不容易暴露：
> 只选中一个单位时两种语义结果相同，**多选时才分叉**。

## 6. Q4 · 动作的可见性

> **动作立即写世界状态；同一 tick 内后续的条件看到的是改后的状态。**

即**顺序敏感**，且这正是想要的：事件表的可读性建立在「从上往下读，像读步骤」之上。
延迟到帧末统一提交（双缓冲）虽然能消掉顺序敏感，但代价是用户读完一条规则**无法预测下一条看到什么**——
那会直接打击 I2。

代价写明：**规则顺序有意义，上下调换规则可能改变行为。** 编辑器要把「调顺序」做成一等操作（§5.3 已有）。

## 7. Q5 · 等待 / 延时的续延

`等待 0.5 秒` 会把规则劈成两半。必须定死三件事：

| # | 语义 |
|---|---|
| **W1** | 等待**挂起的是这一条规则实例的续延**，不阻塞其余规则与其余实体 |
| **W2** | 挂起时**快照当时的实体集**；恢复时用快照，不重新求值条件 |
| **W3** | 快照里的实体若已销毁，恢复时**跳过该实体**，不报错、不整条中止 |

**W2 是存档语义的前提**：等待队列（含其实体集快照与剩余时间）**属于运行期状态，必须可序列化**
（[goals.md §4.5](goals.md#45-两级状态--播放沙箱) 的三种状态固化）。
漏了它，存进度再读档会丢掉所有正在等待的规则——而技能冷却、波次间隔全都是等待。

### 7.2 计时器是一等概念（r2 新增）

`设置 缓冲 = 0.15 秒` 这样带时间单位的变量，**由内核在 step 5 统一按 `dt` 递减，下限截断到 0**。

| # | 语义 |
|---|---|
| **T1** | 声明为计时器的变量自动递减；不声明的数值变量不会 |
| **T2** | 计时器与等待队列**同属运行期状态，同样必须可序列化**（W2 的理由逐字适用） |
| **T3** | 受限 JS 环境注入 `rng` / `tick` / **`dt`**（§8 D3 原本只有前两个） |

**为什么不让用户自己写 `每帧 → 缓冲 = 缓冲 - dt`**：技能冷却、波次间隔、跳跃缓冲、
无敌帧、buff 时长——每个作品都会重新实现一遍，而**忘记把它写进存档**的概率极高，直接撞 I11。
把它做成一等概念，序列化就是内核的责任，不是每个作者的责任。

## 8. 确定性的四条附加约束

本文是 [goals.md](goals.md) 决策 29 的执行点之一。求值层要守：

| # | 约束 | 为什么 |
|---|---|---|
| **D1** | 实体迭代顺序按**稳定 id 升序**，不按 ECS 原型的内存顺序 | 原型式 ECS 的迭代顺序会随组件增删变化（[adr-001](adr-001-ecs.md) §5 第 5 条） |
| **D2** | 事件表可用的随机数**只能**来自内核注入的带种子 rng | 见 D3 |
| **D3** | 用 JS 实现的条件与动作，跑在**受限环境**里：禁 `Date` / `Math.random` / 网络 / 存储，注入 `rng`、`tick` 与 **`dt`**（r2） | **这是决策 29 现存的唯一漏洞**：一个用户写的 JS 条件调一次 `Math.random()`，lockstep 与 headless 断言同时废掉 |
| **D4**<br>（r2） | 同一 step 内产生的触发事件，**入队前按 `(事件类型 id, 主实体 id, 次实体 id)` 升序稳定排序**（tick 流程 step 2.5） | **D1 只做了实体迭代那一半，事件顺序这一半一直缺着。** Rapier 的接触事件顺序来自其内部宽相 / 窄相遍历，**不保证跨平台一致**；顺序不同 → 谁先执行不同 → 世界状态分叉 → lockstep 立即失步。[spike-001](spike-001-rapier-determinism.md) 已把「事件序列一致」加进验收 |

## 9. 三个手工样例（定稿前必须逐个走通）

**判据是可判定的：三个样例各自写出规则行，按第 3–7 节的语义手工推演一遍，
结果与「用户读这段规则会预期什么」一致。任一条不一致 → 改语义，不改样例。**

### 样例一 · 塔防选目标（检验 P1 / P2 / Q3 / R1，r2 改写）

```
每帧
    塔 冷却完毕                      ← 收窄「塔」
    塔 的 射程内 最近 的 敌人         ← 关联查询：为每座塔配对一个敌人（§4.1）
就  塔 朝 配对的 敌人 开火            ← 按配对逐个执行，不是笛卡尔积
    塔 进入冷却
```

要验证：两座塔各打各的最近目标，而不是全部打同一个；范围内无敌人时整条不执行（空集）。

> **r2 为什么改了这个样例的写法。**
> §9 的原则是「结果不一致 → 改语义，不改样例」，这次**没有违反它**——
> 样例的**意图一字未改**（两座塔各打各的最近目标），改的是**表达形式**，
> 因为原写法与它自己声明的意图**在任何语义下都不匹配**：
>
> 原写法用 `当 敌人 进入 塔的范围` 这个**触发型**条件。触发是**逐事件**的，
> 每个事件只携带一对 `(敌人, 塔)`——**载荷里根本没有第二个候选**，
> 「最近」无从选起。三个敌人同 tick 进入，就是三个独立事件，
> 第一个事件让塔开火并进入冷却，后两个事件撞上「冷却完毕」为空集而全部落空：
> **塔打中的是「事件顺序里的第一个」，不是「最近的」。**
>
> 「在一批候选中选最优」本质上是**批量查询**，不是事件响应。它属于常规规则。

**保留的触发型子样例**（检验 A1 / E4）：

```
当  敌人 进入 塔的范围          ← 触发型：载荷 (敌人, 塔)，各为单元素集（A1）
就  塔 播放「警戒」音效
```

要验证：只有触发它的那座塔响应，不是全部塔（A1）；
若该敌人在同 tick 被先前的事件销毁，本事件跳过而不报错（E4）。

### 样例二 · 平台跳跃的跳跃缓冲（检验 E1 / Q4 / W1）

```
当  意图「跳跃」被按下              ← 触发型，无实体载荷 → 角色从全集开始（A1）
就  设置 计时器 缓冲 = 0.15 秒      ← 计时器，由内核递减（§7.2 T1）

每帧
    缓冲 > 0
    角色 在地面上
就  角色 向上施加冲量
    设置 缓冲 = 0
```

要验证：落地前 0.1 秒按的跳跃仍然生效（触发先于全表 → E1）；同一 tick 内先写后读（Q4）；
存读档后剩余缓冲时间保持（T2）。

### 样例三 · RTS 下达指令（检验 P3 / W2）

```
当  意图「确认」被按下              ← 触发型
    存在 被选中的单位
就  被选中的单位 移动到 光标位置

当  单位 到达目标点
就  单位 播放「待机」
    等待 0.3 秒                     ← 挂起时快照这批单位（W2）
    单位 朝向 默认方向
```

要验证：第二条规则不受第一条的选中集影响（P3）；等待期间有单位被摧毁不报错（W3）。

## 10. 冻结与退役条件

- **冻结时机**：三个样例走通 → 本文状态改为「已冻结」，此后按 **I11** 对待，与标识符稳定性同级
- **冻结的范围**：第 3–7 节的语义。**性能优化（脏标记、条件短路、查询缓存）不受约束**，只要可观察行为一致

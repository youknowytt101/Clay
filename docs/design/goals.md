## 零 · 冷启动

只读这一节就能判断一个提议该不该进来。

### 0.1 一句话定义

> **一个 AI 与人共用同一条编辑通道的通用 3D 网页游戏引擎编辑器：
> 游戏逻辑是数据，AI 和鼠标是同一个命令层的两个前端，产出的是同一种材料。**

> **v17 换掉了原来那句**（「一个普通人也能上手的……界面对人友好，底层保持技术性，
> AI 是把两者连起来的那座桥」）。原句把 AI 定位成**桥**——连接普通人与技术底层的中间物；
> 而 AI 现在是**主结构**，不是桥。门槛由 AI 与教程承担（决策 35），
> 但那是这条定义的**推论**，不是它本身。

### 0.2 十二条不变量

违反其中任何一条的提议，直接驳回；真要破，必须先改本节并写明理由。
**v17 改了三条（I2 / I4 / I8），理由在表下。**

| # | 不变量 | 破了会怎样 |
|---|---|---|
| **I1** | 编辑期的一切变更**只能**经由 Action 层 | 撤销、回放、AI 校验全部失效 |
| **I2** | 游戏逻辑是**数据**（事件表），不是代码，且**可读、可逐行 diff、可被约束层校验** | AI 产出变成黑盒；逐行 diff、局部重试、可审计全部失效 |
| **I3** | AI 的产出与人手做的是**同一种材料**，用户能接手继续改 | 同上。**与 I1 并列为护城河** |
| **I4** | 门槛由 **AI 与内置教程**承担，**不靠削能力、不靠做浅底层**（决策 35） | 要么用户跨不过去，要么引擎能力被永久封顶 |
| **I5** | 模块之间只通过**显式契约**通信（组件 / Action / 条件动作） | 模块不可替换，「通用内核」名存实亡 |
| **I6** | 内核只放**至少两款目标游戏需要、且分属不同簇**的东西（决策 39） | 内核膨胀，最可能的死法 |
| **I7** | 任何时候都能**不开界面**跑完整场景并断言结果 | 迭代成本失控 |
| **I8** | 能力面是 registry 的**视图**，不是数据分叉：任何裁剪过的界面都共享**同一份数据、同一套 Action、同一个撤销栈** | 一旦分叉就是两个编辑器，维护翻倍 |
| **I9** | 事件表与玩法组件**不得引用具体美术资源**，只引用语义名 | 玩法与美术焊死，「一种玩法多种风格」不成立 |
| **I10** | 引擎**不得依赖任何单一供应商的独有能力**；能力不足的模型必须能降级运行 | 「接入各种模型」变成空话，用户被锁死在一家 |
| **I11** | **已发布的链接必须永远能打开**：快照自带版本、引擎保留迁移链、标识符只增不改 | 一次重命名就把所有人已发布的作品变成砖 |
| **I12** | 事件表**不得引用具体输入设备与宿主 API**，只引用**输入意图**（跳跃 / 确认 / 移动） | 平台与设备被写进作品；移植时要用户回去改自己的规则 |

**v17 为什么改这三条**：

| 原文 | 改成 | 理由 |
|---|---|---|
| I2「**普通人读得懂**」 | 「**可读、可逐行 diff、可被约束层校验**」 | 「普通人读得懂」曾是护城河的一半，现在护城河是 I1 + I3。**但「逻辑是数据」这件事一条没松**——它现在的理由更硬：逻辑一旦变成代码，AI 的产出就无法走 Action 层、无法逐行 diff、无法局部重试，**I1 直接失效**。见 [A.12](#a12-决策-35为什么门槛可以交给-ai-与教程) |
| I4「界面对普通人友好，底层不因此变浅」 | 「门槛由 **AI 与内置教程**承担」 | 原文把「友好」寄托在界面简化上，代价是双模式与术语层两套机制。**决策 35 换了承担者**：门槛交给 AI 与教程，界面回到一套全集 |
| I8「简易模式与专业模式共享同一份数据」 | 「能力面是 registry 的**视图**，不是数据分叉」 | 双模式已由决策 12 取消。**但这条不变量要留着**——它管的是「任何裁剪界面都不许分叉数据」，日后真要做面向新手的裁剪视图，这条仍然生效 |

### 0.3 术语

**v17 起没有术语层了**（决策 12 取消双模式）。界面直接用工程术语：实体、组件、Action、约束、事件表、规则行、配方、皮肤包、kind、模板、播放模式。
目标用户是有经验的游戏研发人员（决策 19′），这些词是他们的母语，**翻译一遍反而增加理解成本**。

i18n 仍然保留，但它现在只做**语言翻译**，不再兼任「内部词 → 界面词」的映射层。
这是决策 12 取消后**顺带省下的一整套机制**。

### 0.4 已定 / 未定 / 不做

- **已定**：[§2 决策表](#二--决策表)的 42 项 + 上面 12 条不变量。可以被新证据挑战，但不得静默改写。
- **未定**：[§9 未决项](#九--未决项)。每项都有 ID、风险路由、决策截止点与证据要求。
- **不做**：[§3.4](#34-能力与边界)的「封顶」列。提之前先看那张表。

### 0.5 编辑规则

1. **不写发布日期、总工期、人力承诺。** 允许写**相对体量**（S/M/L/XL，不折算成天数）与**技术止损时间盒**（「spike 最多 3 天」——它是实验的退出条件，不是交付承诺，且必须标明是止损）。**v19 精确化**：原文是「不写工期、预算、人力」，与 ADR 需要时间盒的现实冲突
2. **决策表只增不改。** 推翻旧决策要写明推翻了什么、为什么，不要静默改写。
3. **判据必须可判定。** 「达到 Unity 水准」这类说法一律换掉。
4. **单点技术选型另开 ADR**（`design/adr-NNN-*.md`），本文只引用结论。
5. **每次结构性改动更新版本号**并在开头说明这一版确立了什么。
6. **非平凡任务先交决策覆盖与证据契约。** 按 [ADR-004](adr-004-evidence-governed-evolution.md) 区分事实、假设与未知；
   决策面空白不得靠 AI 自行补义，高风险项先挑战或实验，低风险项带回退推进。

### 0.7 ADR 状态机（v19）

**每份 ADR 的状态必须是下面五档之一，且每次转换都要有一个可核验条件。**

```
草案 → 倾向已定 → 已验证 → 已冻结 → 已取代
                ↘  上游已变，待重审  ↙
```

| 状态 | 含义 | 转入这一档的条件 |
|---|---|---|
| **草案** | 还在收集事实 | — |
| **倾向已定** | 方案选好了，验证未做 | 候选已淘汰到唯一，理由写明 |
| **已验证** | spike / 样例推演跑通 | **ADR 自己写明的那个判据通过** |
| **已冻结** | 按 **I11** 对待，此后只许改实现不许改语义 | 已验证 + 下游全部对齐 |
| **已取代** | 被新 ADR 顶替 | 新 ADR 编号写在本 ADR 头部 |
| **上游已变，待重审** | goals.md 改动使本 ADR 的前提或结论失效 | 推翻决策时由 §7.1 第 5 步的全仓扫描发现 |

**第六档是 v19 补的**。ADR-001 曾长期处在这个状态却无处标记：它整体仍有效，
但退役条件被决策 29 作废、上游引用全部指向旧坐标系，而「已定」和「已取代」两档都不对。

**下游不得超前于 ADR 的状态。** ADR 写「倾向已定」时，
`architecture-outline.md` 不许写「已冻结」——这一条由 `check-docs.py` 校验。

## 一 · 产品定义

### 1.1 用户是谁

> **有经验的游戏研发人员。**（决策 19′，v17 推翻原「不写代码的普通人」）

懂关卡设计、数值、状态机、碰撞、帧；用过至少一个商业引擎；**看得懂也写得出代码**。
他们要的不是「更简单的引擎」，是**一条 AI 能真正接手的编辑通道**。

#### 但画像不是设计约束（决策 35）

> **不要用画像去反推该做什么、不该做什么。**

这是 v17 最重要的一句话，因为**原文档正是这么做的**：因为用户是普通人，所以要双模式、要术语层、
要削表达力、要限制概念数量——**四条约束全部由画像推导而来，而画像是全文最容易变的一条假设**。

新的分工是：

| 承担者 | 承担什么 |
|---|---|
| **内置 AI**（决策 8、21） | 「我不知道怎么做」——一句话变成可预览、可撤销、可手改的 Action |
| **内置教程**（决策 35，v17 新增） | 「我不知道有这个东西」——按能力组织的可交互教程，就在编辑器里，不是外链文档 |
| **模板 + 配方**（决策 9、18） | 「我不想从零开始」 |
| **约束层**（§5.1） | 「我做错了但不知道错在哪」 |

**四条合起来替代了原来的「把界面做浅」。** 于是：

- 能力面回到**一套全集**，没有简易/专业之分（决策 12 取消）
- 表达力的封顶**只由技术理由决定**（可校验、可 diff、确定性），不再由「读得懂」决定
- 概念数量**不设上限**，但**每加一个概念，必须同时给出它的教程条目或配方**（§1.4）

**门槛没有消失，只是换了承担者。** 论证见 [A.12](#a12-决策-35为什么门槛可以交给-ai-与教程)。

### 1.2 用户拿到的是什么

```
模板   = 世界状态 + 事件表 + 资产引用 + 皮肤包 + 依赖的模块声明
```

三条推论：

1. **模板是普通工程，不是特殊格式。** 用户改完可另存为自己的作品，也可把作品变成模板。
2. **模板由模块提供**（契约的 `templates` 字段）。
3. **模板必须能被 AI 读懂**——它是 AI 理解「这个游戏在做什么」的入口。

在模板之上，用户手里有四种可改的东西，**全部是同一种材料**：

| 改什么 | 形态 |
|---|---|
| 摆什么 | 物体与属性 |
| 玩法规则 | **事件表**，可从**配方**改起，也可直接写规则行（决策 13、18） |
| 复用与数值 | **行为单元 + 数据表**（§4.7） |
| 让 AI 改 | 一句话 → 若干条 Action，可预览可撤销 |
| 长什么样 | **换皮肤包**（决策 20） |

（v17 删掉了原来的「门槛」列——决策 35 之后，门槛由 AI 与教程承担，不再是每项能力自带的属性。）

### 1.3 用户心流（产品的真正判据）

> **一图版**：[overview.svg](../diagrams/overview.svg) 第 4 图 · 用户流程

**心流有两条**（首次与回访），**中间有一个循环**，**结尾有一条回流**。
不在这张图上的功能，往后排——这比「至少两个模板都需要吗」更贴近产品判断。

#### A · 首次心流：从打开到第一次被人玩

| # | 步骤 | 用户看到什么 | 为什么在这个位置 |
|---|---|---|---|
| 1 | **打开** | **模板库**，几个能直接玩的东西。不是空场景，不是输入框，**不是设置页** | 决策 9。**空白页对谁都是浪费时间**——理由不再依赖画像 |
| 2 | **选一个，先玩** | 点进去直接**试玩**一局 | 先建立「我要做的是这种东西」的目标感。没玩过就开始改，等于闭着眼睛改 |
| 3 | **改一个数** | 改敌人血量 / 跳跃高度 → 再试玩 → **看到差别** | **第一次正反馈**，必须发生在前十分钟 |
| 4 | **改玩法** | 打开事件表，从**配方**入手：改一半、加一条规则行 | 决策 13、18。配方让这一步是「改」，不是「学」 |
| 5 | **让 AI 帮忙** | 「加一种会飞的敌人」→ 看 AI 给出的计划与验收条件 → 批准 → 逐步执行；小改动仍可直接预览变更集 → **自己再手改一行** | 决策 8、40。**I3 在这一刻被用户亲身验证**；v20 起复杂任务先过计划批准门，简单任务不被强迫走长流程 |
| 6 | **换风格 / 调视听** | 换整套皮肤；调材质与光照预设、后处理档位、配上音效 | 决策 20、23。**玩法定了之后才谈表达**——美术是对已定玩法的表达，不是它的前提 |
| 7 | **检查与打磨** | 看每步 diff、约束、headless 断言、输入轨迹与截图证据；失败时审阅修复假设，随时停止或回到任一通过的 checkpoint | 「游戏整合」不是听 AI 宣布完成，而是确认 hard oracle 真通过；证据和恢复点让错误成本可控（决策 40 的 v20 修订） |
| 8 | **导出** | 一个按钮 → **自包含工程文件**，自己收着或发给别人 | **v17 修订**：分享链接与账号整体推后（决 14 / 28）。本轮的终点是导出，不是发布 |

> **v17 对这张表的修订**：
> 第 1 步的理由从「普通人怕的不是复杂，是不知道从哪下手」改为「**空白页对谁都是浪费时间**」——
> 决策 9 的结论不变，理由不再依赖画像。
> 第 7 步删掉「在手机上试一次」（移动端本轮出局）。
> 第 8 步从「发布 + 注册」改为「导出工程文件」。
> **新增一条贯穿始终的旁路**：任何一步都能唤出**内置教程**（决策 35），
> 它不挡在路上，但永远在手边——这是「模板优先，空白页有罪」与「教程」的正确关系，
> 原文档否掉的是**「空场景 + 教程」作为入口**，不是教程本身。

**关于第 6 步的位置**：换皮仍然是**成本最低、成就感最高**的一步，但它排在玩法之后——
**先知道这游戏是什么，再决定它长什么样**，这也是真实制作的顺序。

两条推论：

- **第 3 步的分量因此更重**：第一次正反馈只能靠「改一个数 → 看到差别」，
  不能指望换皮来兜底。这一步的手感要打磨到位
- 换皮落在**导出前一步**，天然成为「让它成为我的作品」的收尾动作

#### B · 主循环（第 3–7 步真正的形状）

制作不是线性的。上面 3–7 步实际是一个循环，**每一圈都要短**：

```
        ┌───────────────────────────────┐
        ↓                               │
   改点东西  →  试玩  →  看到差别 / 看到问题
   （物体 / 规则 / 让 AI 改 / 风格）      │
        ↑                               │
        └───────── 不满意就撤销 ─────────┘
```

三条支撑它的机制，全部已在计划里：**播放沙箱**（退出即回滚，试玩不污染工程）、
**任何操作都能撤销**（含 AI 的）、**约束层当场说人话**（不用等到试玩才发现错）。

**循环的长度是产品质量的核心指标**：从「改」到「看到结果」超过几秒，心流就断了。

#### C · 回访心流：第二次打开

```
打开 → 项目门厅（我的作品 + 最近编辑 + 模板库）→ 直接回到主循环
```

回访用户**不该再看一遍模板库的推销**，也不该重新选类型。已有的项目门厅正是这一步。

#### D · 回流：remix 让终点变成起点（**v17 推后**）

```
你发布 → 朋友打开链接玩 → 点「改成我的」 → 他从第 3 步开始
```

决策 14 的循环是「做 → 分享 → 被玩 → 被 remix → 再做」，
**它仍然是长期目标，但整条链推到开放阶段**（§6 阶段四）。
本轮的等价物是**导出工程文件**：自包含、能发给别人、别人打开就能改。
**remix 的语义因此现在就成立，只是走文件而不是走链接。**

#### E · 关于「设置 AI 模型」在哪一步

> **不在创作路径上。**（决策 22，v14 收窄，v17 再次收窄）
>
> v17 起**全流程都不问账号**——发布与注册整体推后。
> 剩下的唯一按需触发项是 **API key**。

把配置 API 放在第 3 步，等于要求一个还没玩到任何东西的人**先完成一次技术配置**——
这是整条路径上最强的流失点，而且与决策 9「打开即有能玩的东西」直接冲突。

正确的位置是**按需触发**，三个入口：

| 触发时机 | 用户看到 |
|---|---|
| 内置额度用完 / 想用更强的模型 | 「换成你自己的模型？」——就在 AI 面板里，不用去翻设置 |
| 想让数据不出本机 | 隐私说明旁边一个「用本地模型」 |
| 主动去设置页 | 随时可以，但**不主动挡路** |

配置本身要好用（预设 + 自定义端点 + 测试连接 + 用量可见），细节见 [§5.5](#55-模型接入决策-21)。

#### F · 每一步对应的决策与闸门

写这张表是为了保证心流与决策**互相咬合**，任何一步都能追溯到判据：

| 步骤 | 决策 | 闸门判据 |
|---|---|---|
| 1–2 打开 / 选模板试玩 | 9、15′ | C.1 C.2 |
| 3 改一个数 | 35（教程可达） | D.5 |
| 4 改玩法 | 13、18、25 | **D.5 教程可用性**、F |
| 5 让 AI 帮忙 | 8、21 | D.1 D.2 **D.6 换模型仍可用** |
| 6 换风格 / 调视听 | 20、17、23 | **C.5 换皮不变** |
| 7 检查与打磨 | I7、约束层、25 | C.3 D.4、**F 完整作品** |
| 8 导出 | 24（P1 分包）、§3.6.3 | C.4 导出的工程文件能在另一台机器打开并继续改 |

**心流走通一遍 ≠ 闸门 F 通过**：心流验的是「路顺不顺」，
**闸门 F 验的是「能不能靠这条路做出一款完整作品」**（§3.1）。

### 1.4 四条设计原则

| 原则 | 内容 |
|---|---|
| **每个概念自带入口**（v17 换掉「概念预算」） | 概念数量**不设上限**——目标用户理解 ECS、状态机、确定性。但**每加一个概念，必须同时交付它的教程条目或配方**，否则那个概念等于不存在。这条比数量上限更可判定，也不依赖画像 |
| **模板优先，空白页有罪** | 先给一个能玩的东西，再让人改它。**空白页对谁都是浪费时间**——理由不再依赖画像 |
| **AI 是主入口，不是侧边栏** | AI 是修改东西的默认方式之一；但产出必须落成能看见、能手改的规则行与物体，**绝不是黑盒** |
| **错误必须便宜** | 任何操作都能撤销（含 AI 的）；不合法的操作当场拦住并给出结构化原因；播放出错不白屏，能回到编辑状态 |

### 1.5 一套能力面（决策 12 于 v17 取消）

> **原来这里是「简易 / 专业双模式」。v17 取消了它。**

取消的理由不是它设计得不好，是**它的前提没了**：双模式、术语层、参数裁剪、受限默认值，
全部是从「用户是不写代码的普通人」推导出来的。画像一改（决策 19′），四样东西同时失去依据，
而它们的维护成本是实打实的——**风险 8「两种模式退化成两个编辑器」也随之消失**。

**现在只有一套能力面：全集。** 但**机制留着**：

| 保留的 | 形态 | 为什么留 |
|---|---|---|
| **能力面是 registry 的视图**（I8） | Action registry 支持按标签过滤，**本轮不实现任何过滤视图** | 日后真要做面向新手的裁剪界面，这是入口；且它本来就是 registry 的自然能力，留着不花钱 |
| 相机档位 | 四档全给，**默认不再是受限俯视** | 决策 16 的「受限」是为零基础用户设的默认值；对目标用户，默认给回自由 |

> **新纪律（替代原来的单向白名单）：新功能直接进全集。
> 要论证的不再是「该不该暴露」，而是「它的教程条目与配方在哪」**（§1.4）。

### 1.6 通用性服务谁

| | 谁 | 怎么用 |
|---|---|---|
| **生产通用性** | 你 / 模块作者 | 写模块、写条件动作、做模板与皮肤 |
| **消费通用性** | 用引擎做游戏的人 | 选模板、改参数、写规则行、定义行为单元、换皮肤、让 AI 改 |

**v17 的变化**：原文说「普通人不直接消费通用，他消费的是模板 + 配方」。
现在两层的**边界模糊了**——有经验的研发人员会在两层之间来回走：今天用配方，明天拆开改，
后天自己写一个条件动作。**这正是决策 18「同一份材料」想要的结果**，只是原来假设用户永远停在消费侧。

## 三 · 范围

### 3.1 目标水位与成功判据（决策 25）

> **一个通用内核 + 若干领域模块 + 事件表逻辑层 + AI 作者接口 + 分享 remix 闭环，
> 合起来让一个人不写代码就能做出一款完整作品，并且做完有人玩。**

**目标水位 = 完整作品，不是 AAA。**

| | 要达到 | 明确不对标 |
|---|---|---|
| 参照 | **内容规模**上是《星露谷》《空洞骑士》这一档：一个人能做完、有头有尾、能上架 | 塞尔达 / CS / Dota 的**成品**——那是 300 人 × 5 年，或竞技网络与运营，不是编辑器功能问题 |

> **v17 提醒**：上面三款参照全是 2D，它们参照的是**内容规模**，不是技术形态。
> 「一个人能做完」这个水位是从 2D 案例借来的，**3D 的实际成本还没被参照过**——
> 这一点写在这里备查，见 [A.11](#a11-决策-4只做-3d-的依据补于-v16) 记下的代价。
>
> **注意区分**：本节说的「不对标塞尔达」指的是**成品**。
> 而 [A.9](#a9-主流玩法压力测试) 判定塞尔达的**核心玩法循环**可做——那是两种不同的判定，
> 且八款目标游戏用的是后者。

#### 唯一的总判据

> **一个人用这个编辑器，做出一款能发到 itch.io 上的完整作品：**
> 标题画面 → **至少 3 个关卡** → **能存进度** → **有技能或道具系统** → 有胜负结算 →
> 有音画 → **30 分钟以上内容**。
>
> **v17 三处修订**：删掉「不写一行代码」（目标用户会写代码，且专业模式本来就允许用 JS 实现条件动作——
> 真正要守的是**逻辑必须是数据**，那由闸门 F 的「没有一行专门为它写的硬编码 JS」管着，见 §6）；
> 删掉「手机能玩」（移动端出局）；**验收人 = 项目所有者**（决策 25 的 v17 修订）。

这条替代了原来的「能改出一个和模板明显不同的关卡」——那是**验证判据**，不是产品判据。

#### 分项判据

| 判据 | 要达到 | 明确**不**追求 |
|---|---|---|
| 世界会自己运转 | 单位、波次、经济、技能、状态能跑通 | 大世界模拟 |
| **游戏有长度** | **多关卡 + 存进度 + 流程**（§4.7） | 云存档、多存档槽管理 |
| **玩法有深度** | **技能 / 道具 / buff 靠可复用行为单元表达**（§4.7） | 图灵完备脚本 |
| AI 真的好用 | 一句话生成 / 修改关卡与逻辑，可预览可撤销 | 一句话生成整个游戏 |
| **上手成本可控**（v17 换掉「普通人能上手」） | **每个概念都有教程条目或配方**；一个懂引擎但没用过本编辑器的人，能靠内置教程 + AI 走通主循环 | 零基础可用；也不追求「不看任何东西就会」 |
| 玩法与美术可分开迭代 | 换一套皮肤，一行规则不改，断言结果一致 | 皮肤市场、节点式材质编辑器 |
| 作品拿得出手 | 有声音、**动画有状态机与 root motion**、有特效 | 3A 视觉、影视级效果、IK 与动作匹配 |
| ~~做完有人玩~~ | **v17 推后**：本轮的等价物是「导出的工程文件能在另一台机器打开并继续改」 | 社区、账号、排行、货币化 |

### 3.2 范围纪律（判据源于 v17 更换 —— 决策 39）

> **任何功能进内核之前必须回答：至少两款目标游戏需要，且分属不同簇吗？
> 只有一款、或都在同一簇 → 进模块。都不需要 → 不做。**

**为什么换判据源**：原判据是「至少两个模板都需要」。而 v17 之后**只剩两个模板**，
「两个都要」就等于「全都要」——**纪律会静默失效**，且失效时没有任何信号。

新的判据源是**八款目标游戏 + 两个簇**：

| 簇 | 游戏 |
|---|---|
| **俯视指令簇** | 红警、星际争霸、魔兽争霸、Dota 2 |
| **第三人称动作簇** | 塞尔达、艾尔登法环、刺客信条、第三人称射击 |

**「分属不同簇」这半句是关键**：四款 RTS 共同需要的东西（比如生产队列的具体形态）
只证明了 RTS 需要它，不证明它该进内核。**跨簇才算通用。**

内核每多一个领域概念，模块的可替换性就低一分。**膨胀的内核不是「做得多」，是做错了。**

这条纪律是**双向**的：v4 把物理请回内核、把寻路砍进塔防模块；
**v17 又按新判据把寻路与视野请回了内核**（决策 38）——判定随事实改判，两次都是。见 [§5.2](#52-内核归属论证)。

### 3.3 成品感下限（决策 23）

> **引擎必须保证：用户不写一行代码，也能做出「看起来、听起来像成品」的东西。**

理由不是审美洁癖，是两条已定决策的直接推论：

**v17 换了理由，结论不变**（分发链推后后，原来两条依据都失效了）：

- **八款目标游戏里四款是第三人称动作**。动画过渡、判定盒特效、打击音效**不是修饰，是玩法反馈的一部分**——艾尔登的硬直、塞尔达的元素反应，缺了视听就无从判断游戏在发生什么
- **决策 25 的水位没变**：一款能上架的完整作品，视听下限是它的一部分

原来的两条依据（作品要发给别人玩、用户有美术底子）随决策 14 推后与画像更换一并失效，**但它们支撑的结论被新依据接住了**。

因此原来那张扁平的「不做」清单被拆成两张：**范围可以砍，质量下限不能砍。**

#### 体素 / 瓦片世界的留口条件（v17 补）

**留口不是「以后大概能加」，是「加的时候不用重写、不破 I11」。** 这一项要守住三条：

| # | 条件 | 为什么 |
|---|---|---|
| **V1** | **块（决策 30）的边界与实体无关**——块是空间分区，不是「一组实体」。日后体素数据按块存取，与实体按块存取走同一套序列化 | 若块被实现成「实体集合」，体素数据无处安放，要重做分块与流式两套机制 |
| **V2** | **kind 注册表不假设「一个 kind 一个实体」**——允许一个 kind 描述一类**格子内容**（材质、通行性、耐久） | 体素世界里「石头」不是实体，是几百万个格子的一种取值。kind 若与实体一对一绑死，皮肤包机制无法覆盖体素 |
| **V3** | **空间查询接口不假设查询对象是刚体**——射线与范围查询留一层抽象，体素地形是它的另一种实现 | 否则事件表里所有「碰到 / 在范围内」的条件都要为体素再写一遍 |

**满足这三条即可**。本轮**不做**：体素存储、贪心网格化、光照传播、地形生成、破坏与放置的编辑工具。

**为什么留口而不封顶**：封顶的含义是「要做就得先推翻决策」，
而这一项没有任何决策否定过它——它只是**没被任何一款目标游戏需要**。
排期问题不该写成方向问题（决策 26）。

#### 方向性封顶

这些不是排期问题。要做就得先推翻对应决策。

| 封顶 | 依据 |
|---|---|
| 2D 一等公民（Sprite 管线） | 决策 4。2D 用正交相机应付，图标用 billboard |
| 让写 JS 成为编排逻辑的主路径 | 决策 6。**v17 澄清**：目标用户会写代码，JS 实现条件与动作是**正常路径**不是高级门；但**编排必须是数据**——那是 I1 与 I3 的前提，不是能力问题 |
| 图灵完备的事件表：任意控制流、递归 | 决策 18 + I2。**v17 换理由**：原理由是「保住普通人读得懂」，现在是**保住可校验、可逐行 diff、可局部重试**——AI 通道的三个前提 |
| **动画档 3**：IK / 动作匹配 / 上下半身分层 | 决策 36。对四款 RTS/MOBA 零贡献，且是无底洞。**代价写明：刺客信条只到「潜入 + 战斗 + 沿预设点攀爬」，没有丝滑跑酷** |
| **竞技 FPS 路线**：服务器权威 + 客户端预测 + 延迟补偿 + 反作弊 | A.9。与 lockstep 亲和性相反，会让网络模型裂成两套，成本大一个数量级 |
| 用削表达力换易懂 | 决策 18。**v17 加强**：门槛由 AI 与教程承担（决策 35），表达力的封顶**只由技术理由决定** |
| 节点图作控制流 / 画布 / 连线 / 布线算法 | 决策 13。节点图只用于数据流 |
| 自研物理 / 自研文生 3D / 自研音频引擎 | 集成 Rapier；文生 3D 接 provider；音频用浏览器原生能力 |
| 风格过强的成套素材（儿童卡通风等） | **v17 换理由**：原理由是画像。现在是**决策 20** —— 内置素材要能被任意皮肤包覆盖，风格太强的素材会让「换皮」失去意义 |
| **产出不可寻址、不可手改的黑盒结果** | I3。**v18 改写**：原文写的是「聊天框一句话生成整个游戏」——**那把规模当成了封顶对象，而该封顶的是形态**。任务多大都可以（决策 40），只要产出仍是 Action 序列、仍落成能看见能手改的规则行与物体 |
| 用用户的 key 做用户没要求的事 | 决策 21 |
| **界面能力面的数据分叉** | I8（决策 12 取消后仍生效）。日后要做裁剪视图，它必须是 registry 的一个视图，不能是第二套数据或第二套 UI 代码 |
| 开场向导 / **创作路径上的注册墙** | 决策 22 + 28。**v17：全流程零账号** |
| describe 输出自然语言 | 引擎输出结构化数据，组织语言是模型的事 |
| 道路系统新功能 | 决策 10。冻结见 [§8](#八--存量资产处置) |

**能力项都过了范围纪律**：至少两个模板都要（见 [§5.2](#52-内核归属论证)）。只有一个模板要的，进模块。

### 3.5 内容包（决策 27）

模板、皮肤、配方、素材、模块**最终都要能被别人拿去用**。本轮不做交易与上架，
但**从现在起它们必须是同一种东西**：

```
内容包 = { 稳定 id, 语义化版本, 作者, 许可, 依赖(包 id + 版本), 内容哈希, 载荷 }
```

- 模板 / 皮肤包 / 配方 / 素材集 / 领域模块，**都是内容包的一种形态**，不是五套机制
- 作品记录**它依赖了哪些包与版本**；remix 时按此解析
- 包的 id 与版本遵守 **I11**：只增不改，否则市场上线后所有引用同时失效
- 本轮**不做**：上架、支付、审核、分成

**账号的边界**（决策 22 + 28）：**创作路径永远不需要账号**——打开、试玩、改、换皮、用 AI，
七步全程不问；**账号只出现在第 8 步「发布」**。理由是作品归属：匿名发布的作品，
日后做市场时认领不回来。


### 3.6 工程底线

四条与功能无关、但**漏了就要返工**的约束。它们不是「做不做」的选择题，是**边界条件**。

#### 3.6.1 性能预算

**v17 起这几个数字服务的是闸门 C.3（1000 单位不掉帧）与闸门 F**，不再是「手机上打开就能玩」。
没有数字，判据不可判定。**超了就砍功能，不放宽数字。**

| 指标 | 上限 |
|---|---|
| 播放期首包（不含用户素材） | **≤ 8 MB** gzip（v17 放宽：移动端出局，4G 冷启动不再是约束） |
| 桌面冷启动到可玩 | **≤ 5 秒** |
| 目标帧率 | 桌面 **60fps**（v17：手机 30fps 一档移除） |
| 同屏**完整模拟**实体 | **1000** 不掉帧（场景总量不设上限，按块加载——决策 30） |
| 单块加载耗时 | **≤ 1 帧预算**，不得造成可见卡顿 |

**v17 的改动与它的代价**：移动端出局后这几个数字全部松了，
但 **P1「播放期与编辑器分包」不能跟着松**——它现在的理由从「3MB 首包」换成
**决策 24 的移植退路**（§3.6.5）。**这是全表唯一一处不允许放宽的**：
首包大小可以谈，分包不能谈，否则日后套壳要把整个编辑器打进去。

**这条会倒推架构**：3 MB 的播放期首包，意味着**播放期与编辑器必须分包**——
渲染桥 + 事件表运行时不得依赖任何编辑器 UI（这一条 §3.5 的分享专条已经要求过，
这里给了它一个可测量的理由）。

#### 3.6.2 发布即产生外部契约（不变量 I11）

**一旦有人发布了链接，引擎的数据格式就有了外部使用者。**

- **标识符只增不改**：`kind` / 条件动作 / 配方 / 皮肤插槽 / 内容包的 id **发布后即冻结**；
  要改就新增一个，旧的标 deprecated 并保留迁移
- **可判定的判据**：半年前发布的链接，今天必须还能打开；迁移链每加一版，回归测试补一条

代价很具体：第一次重构条件动作命名，**所有已发布作品同时变砖**。
三种存档各自的版本与权威见 [§4.5](#45-两级状态--播放沙箱)。

#### 3.6.3 本地数据是脆弱的

决策 14 说「工程的权威副本始终在用户本地」。网页端的「本地」是 IndexedDB——
**用户清一次浏览器缓存，作品全部消失，而他只会怪你。**

| 必须有 | 说明 |
|---|---|
| **自动保存** | 不做 Ctrl+S 文化。**IndexedDB 没有「文件在磁盘上」这个心智模型**，忘存的代价是全丢，和用户是谁无关 |
| **导出工程文件** | 一个自包含的工程文件，用户能自己收着、能发给别人 |
| **明确告知** | 第一次保存时说清作品存在哪、清缓存会怎样 |

桌面外壳没有这个问题，网页版有——**而网页是主形态**。

#### 3.6.4 用户内容的安全面

remix 意味着**在自己的域下执行别人的数据**。事件表不图灵完备降低了逻辑风险，但没解决这三条：

| 面 | 对策 |
|---|---|
| **游戏内 UI 是 DOM overlay，而用户会往里写文案** | 一律 `textContent`，**禁止 `innerHTML`**。这是最现实的一处 XSS |
| 导入与快照解析（glTF、贴图、快照本身） | 体积与资源数上限；解析失败要**优雅失败**，不能崩掉整个编辑器 |
| 快照体积炸弹 | 上限见 §9，超限直接拒绝发布 |

**这一条必须在做分享之前落地**，不是分享做完再补。

#### 3.6.5 移植退路（决策 24）

**本轮不做导出**（§3.5 未变）。但「日后能不能低成本变成端游 / 手游」取决于现在的三个约束，
**漏了就要改用户已经做好的作品**——那是最贵的一种返工。

先说清楚这条路的实际成本，免得日后高估或低估：

| 目标 | 技术成本 | 真正的成本 |
|---|---|---|
| **PC 端游** | 几乎为零：播放期 + 快照塞进 Tauri / Electron 壳 | 代码签名与公证、安装包体积、自动更新 |
| **手游 · 加到主屏（PWA）** | 零 | 上不了商店，无内购 |
| **手游 · 套壳上架** | 低，几天量级 | **性能与合规**：中低端安卓 WebView 上的 3D + WASM；iOS 的 WebGPU 进度与音频手势限制；商店对 UGC 的额外审核 |
| 原生重写 | 高 | 只在前三条都不够时才考虑 |

**保住它的三条约束：**

| # | 约束 | 漏了会怎样 |
|---|---|---|
| **P1** | **播放期与编辑器分包**（§3.6.1 已因性能预算成为硬要求） | 套壳时要把整个编辑器打进去 |
| **P2** | **输入意图映射**（I12）：事件表写「当**跳跃**被按下」，不写「当**空格**被按下」。设备绑定是一张**可换的映射表**——和皮肤包同一个模式（决策 20） | 移植到手柄 / 触屏时，**用户要回去改自己的规则** |
| **P3** | **宿主能力抽象**：全屏、指针锁定、URL、存储、文件读写各留一层薄接口，浏览器是其中一种实现 | 运行时和浏览器焊死，套壳时到处改 |

**「回炉重造」能到什么程度**——取决于改的是实现还是语义：

- 改**实现**（换 ECS 库 / 换渲染器 / 换物理 / 换宿主平台）→ 作品留得下来。
  因为作品是**数据**（事件表 + 组件表 + 皮肤映射 + 输入绑定），换的是解释器
- 改**事件表的求值语义**（求值模型、规则行之间实体集的传递规则）→ **迁移链救不了**：
  作品还能打开，但跑出来的行为变了

> **所以真正需要冻结的不是渲染层，是事件表的求值语义。**
> 它现在还在 §9 未决项里；**阶段二一旦定下，即按 I11 的标准冻结**，与标识符稳定性同级。
> 这是全项目唯一一处「定错了没有退路」的地方。

## 四 · 架构

> **一图版**：[overview.svg](../diagrams/overview.svg) 第 1 图 · 系统全景（另见第 2 图数据模型、第 3 图一帧发生什么）

> **贯穿全篇的一个模式：可替换的东西都是一张映射表。**
> `kind -> 视觉`（皮肤包）、`动画语义状态 -> clip`、`输入意图 -> 设备`、`包 id + 版本 -> 内容`——
> 四处用的是同一招：**把易变的东西挪出玩法层，用一张能整体替换的表隔开**。
> 后面各处只引用这个模式，不再重复解释。

### 4.1 分层

```
                   ┌──────────────────────────────────┐
   模板库  ───────►│  编辑器 UI（简易 / 专业双模式）   │◄────── AI 作者接口
                   └────────────────┬─────────────────┘
                                    ▼
                   ┌──────────────────────────────────┐
                   │  Action 层（唯一编辑期变更入口）  │
                   └────────────────┬─────────────────┘
                                    ▼
                   ┌──────────────────────────────────┐
                   │  ECS 封装层（自写）               │
                   │  defineComponent / query / schema │
                   └────────────────┬─────────────────┘
                                    ▼
                   ┌──────────────────────────────────┐
                   │  第三方 ECS 库（koota，可替换）   │
                   └──────┬───────────┬───────────┬───┘
                          ▼           ▼           ▼
                ┌──────────────┐ ┌─────────┐ ┌────────────────┐
                │ 事件表运行时 │ │ 系统(JS)│ │ 渲染桥          │
                │ 播放期逐行   │ │ 播放期  │ │ 组件+皮肤→three │
                └──────────────┘ └─────────┘ └────────────────┘
                          ▲
                ┌─────────┴──────────┐
                │ 领域模块            │  RTS/MOBA · 第三人称动作
                │ = 组件 + 系统 +     │  各自注册组件、Action、
                │   条件动作 + kinds  │  条件动作、约束、面板、
                │   + 约束 + 皮肤 +   │  皮肤包、模板
                │   模板              │
                └─────────────────────┘
```

**封装层是硬约束**（见 [adr-001-ecs.md](adr-001-ecs.md) §4.1）：模块与系统代码**一律不得直接 import 第三方 ECS 库**。它承担三件事——组件 schema（库不提供）、模块契约的执行点、把库选型从地基决策降级为可替换模块。

### 4.2 Action 层：唯一变更通道

编辑期世界状态只能通过 Action 改变。鼠标、AI、事件表编辑、读档全部收敛到同一入口。

```
场景 = 初始状态 + Action 序列
```

这是**语义模型**（用于 diff、回放、审计），不是存储实现。

**现状**：[History](../../js/core/History.js) + 17 个 Command 已是这根支柱的九成，差的是「唯一入口」的强制。

**v20 增加步骤事务语义**（[ADR-003](adr-003-verified-agent-loop.md)）：复杂任务的每个计划步骤绑定
`baseRevision`，先在候选分支 `preview`，通过已批准的 hard oracle 后才 `commit` 并形成 checkpoint；
失败或取消 `abort`，不得把半批 Action 留在主工程。`idempotencyKey` 防重复执行，实际 `affects`
超出计划作用域立即停止。Action 层仍是唯一状态真源，计划与证据不是第二套世界状态。

### 4.3 逻辑是数据：事件表 + 配方

```
当  敌人 进入 塔的范围
    塔 冷却完毕
就  塔 朝 敌人 开火
    等待 0.5 秒
```

一条规则 = 若干**条件行** + 若干**动作行**，可分组、**可嵌套子事件**。没有画布、连线、坐标。

**表达力档位**（决策 18，v8 放宽）：条件 / 动作 / 分组 / 全局与对象变量 / 等待 / 重复 N 次
/ **多层子事件** / 参数位的**简单算术与比较**（伤害公式这类东西没有它写不出来）。

#### 配方 = 行为单元的预设（v15 合并）

v11 加了「行为单元」之后，配方与它的约束几乎重复（R1 与 B1 说的是同一件事）。
**现在只有一种机制**：

> **配方 = 一个行为单元 + 一组默认参数 + 一句人话说明。**

于是学习路径是连续的，四步走的是同一样东西：

```
用配方  ->  改它的参数  ->  展开看里面的规则行  ->  自己定义一个行为单元
```

三条硬性质（原 R1-R4 与 B1-B3 合并后的结果，见 §4.7）：

| # | 性质 | 为什么 |
|---|---|---|
| **R1** | 展开后是**普通规则行**，不是黑盒 | 破了就违反 I3 与 M3 |
| **R2** | **可以只改一半**，改完还是好的 | 「一边学一边改」的字面要求；展开成内联规则后天然成立 |
| **R3** | 带一句人话说明 | 学习发生在阅读那一刻，不在文档里 |

**AI 也走同一条路**：优先挑配方、填参数，只有配方都不合适才逐行拼（原 R4）。

**JS 没有消失，它下沉了**：用 JS **实现新的条件与动作**是正常路径（v17：目标用户会写代码，这不再是「高级门」）。
但**条件动作的实现是代码，它们的编排是数据——两者不混**。

> **这条边界是 I1 与 I3 的前提，不是能力问题。** 编排一旦变成代码，
> AI 就无法走 Action 层、无法逐行 diff、无法局部重试、无法被单独撤销。
> **判断一段 JS 该不该存在的判据**：它能不能被另一个模板复用（闸门 F 用的也是这一条）。
> 实现受**确定性沙箱**约束（§7.1 J1–J3）。

### 4.4 呈现与玩法分离：皮肤包（决策 20）

> **玩法量属于逻辑，呈现量属于皮肤包，皮肤包不得改变玩法量。**

```
实体   = { kind: "enemy.walker", 位置, 玩法组件… }
皮肤包 = kind → { 模型, 材质, 缩放, 动画状态映射, 图标 }
```

| 机制 | 内容 |
|---|---|
| 间接层 | 实体持有语义种类，不持有模型。渲染桥在皮肤包上解析。**换风格 = 换一张表** |
| 玩法量归逻辑 | **碰撞体与占地由 kind 定义**；模型按插槽适配到该尺寸，视觉可溢出但**不参与碰撞** |
| 语义名（I9） | 写 `播放「跑」` 不写 clip 名；写 `生成 敌人.走路兵` 不写模型路径。缺失回退到「站立」+ warning，不崩 |
| 契约 + 约束 | 契约声明 `kinds` / `skins`；约束「皮肤包完整性」检查当前皮肤是否覆盖用到的每个 kind 与动画状态 |

#### root motion 撞上了这一节的两条规则（v17 新增）

决策 36 把 root motion 放进本轮，而它**同时撞上两条已有的硬规则**。两条都有解，但必须写死：

| 冲突 | 解法 |
|---|---|
| **① root motion 违反「视听层只读」**——它的字面意思就是动画驱动位移，即渲染层写玩法状态 | **导入时把 root 曲线烘焙成位移曲线，作为玩法数据。** 运行期玩法层读烘焙结果（确定性、可序列化、可断言），渲染层仍然只读。不这么做，闸门 A 的逐字节断言会随机失败 |
| **② 位移曲线若归皮肤包，换皮就改变玩法**——不同皮肤的攻击动画前冲距离不同，闸门 C.5 当场破功（违反 I9） | **位移曲线归 kind，不归皮肤包。** 这完全套用本节已有的模式：「碰撞体与占地由 kind 定义，模型按插槽适配到该尺寸」——现在多一句：**kind 声明每个动画状态的位移曲线，皮肤包提供的 clip 必须适配到这条曲线，而不是反过来** |

**一句话**：**root motion 的位移是玩法量，动画只是它的表现。** 和碰撞体是同一个道理。

**运行期的对应规则：视听层是只读消费者。**

> **动画、粒子、音频、后处理不得写入任何玩法组件——单向数据流。**
> 且所有「逐字节一致」的断言，**范围限定在玩法状态**，不含渲染与视听状态。
>
> **动画状态机（决策 36）也受这条管**：状态机的**当前状态是玩法数据**（事件表能读能写），
> 而 clip 选择、混合权重、过渡时长是**呈现**，归皮肤包。换皮不得改变状态机的状态转移。

I9 管的是编辑期（事件表不引用美术资源），这条管的是播放期。
少了它，闸门 A / C.3 / C.5 的断言会随机失败，而且极难排查——
你会以为是皮肤包设计错了，其实是断言范围没定义清楚。

**判据（闸门 C.5）**：换一套皮肤包，一行规则不用改，headless 同输入下**玩法状态**逐字节一致。
不一致 = 有美术量泄漏进玩法，**且能精确指出泄漏在哪**。

### 4.5 两级状态 + 播放沙箱

| | 编辑期 | 播放期 |
|---|---|---|
| 谁是权威 | **Action 层** | 事件表运行时 / 系统 |
| 允许直接写状态 | 否 | 是 |
| 撤销栈 / 变更日志 | 有 | 无 |
| 约束校验 | 实时 | 不校验 |
| AI 可介入 | **是** | **只可经试飞台驱动输入并读取观测，不得直接写玩法状态** |

进入播放 = 打快照；退出播放 = 整体回滚。**播放期的改动不污染工程。**

因为玩法是数据而不是任意 JS，播放期也能做成确定性的（固定步长 + 可注入种子 + 可脚本化输入序列），于是拿到
**脚本化试玩 + 断言**。v20 起它不再只是「AI 自己试玩并报告」，而是 [ADR-003](adr-003-verified-agent-loop.md)
的 V2 行为 oracle：同一输入轨迹与 seed 可重放，hard 失败不能被截图描述或模型自评覆盖。
**v14 起，逐帧严格确定性是硬要求，不再允许降级为统计式**（决策 29）。
依据见**决策 29 的 v17 修订行**（§2）：八款目标游戏里五款是联机游戏，且全部走 lockstep。

> **v18 记录**：此处原本链接到「附录 A.10 · 决策 28 / 29 / 30 的依据」，
> 而**那一节从未写出来**（v15 沿革声称新增了它，实际没有）。
> 不补写——决策 29 的依据已在 v17 被换掉，A.10 即使补出来也是过期论证。

#### 三种「状态固化」

引擎里有三处把状态写下来，**它们是同一个模式的三种作用域**：

| | 工程存档 | 发布快照 | 运行时存档（存进度） |
|---|---|---|---|
| 存什么 | 编辑期世界状态 + 流程 + 事件表 | 工程的只读固化 | 游戏自己声明的持久化状态 |
| 谁定义格式 | 引擎（版本化信封 + 迁移链） | 同左 + 内容哈希 + 作者 id | **游戏自己声明存什么** |
| 权威 | Action 层 | 发布那一刻的工程 | 事件表运行时 |
| 带版本 | 是 | 是（**I11**：永远能打开） | 是 |
| 上传 | 否（本地，可导出） | 是 | 否 |

**v11 改判**：运行时存档原来写「不做」。那条在技术上成立、在产品上说不通——
不提供存进度，用户只能做几分钟的小品，与决策 25 冲突。

### 4.6 为什么 ECS（用户不可见的选择）

不是性能理由，是**可寻址性**：

- 世界状态 = 扁平数据表 → AI 能查询
- 结构扁平同构 → schema 好写（schema 不是 ECS 白送的，由封装层实现）
- 无层级嵌套 → diff 干净、序列化稳定、约束谓词好写
- 系统是纯函数式表变换 → 确定性容易保证，headless 试算容易

节点树在这四条上全部更差。**性能是附赠的，不是理由。**

### 4.7 完整作品需要的五个概念（决策 25、32、37）

塔防和平台跳跃这两个模板**恰好都不需要**下面几样东西——所以 v11 之前的架构漏掉了它们。
**用一局几分钟的模板去倒推架构，倒推不出完整游戏需要的东西。**

它们的共同点：**现在不设计，以后加就要改数据模型或废掉已发布的作品（撞 I11）。**
所以**数据模型现在就定，实现可以分批**（决策 26）。

#### 1 · 场景与流程

```
工程 = 若干场景 + 一张流程（哪个场景先来、什么条件切到下一个）
     + 全局状态（金钱、解锁、当前关卡…）
```

- **场景**是可独立编辑、独立试玩的单位；一个工程不再只有一个场景
- **流程**本身是数据（不是代码），因此也走 Action 层、也能被 AI 读写
- **界面页**（标题 / 暂停 / 背包 / 对话 / 结算）是流程里的节点，用 DOM overlay 实现
- 切换场景时，**全局状态保留、场景内状态重置**——这条语义要写死，否则存档语义会跟着漂

**场景与块的关系**（决策 30 引入「块」，这里定死两者边界）：

> **场景是流程与存档的单位；块是场景内部的分区。**
> 一个场景 = 若干块；切场景 = 卸载全部块，再加载新场景的块。

这条不写死，阶段一会同时撞上「按块序列化」和「场景切换」两套语义。定死之后：
存档按场景组织、加载按块组织，互不干涉。

#### 2 · 可复用的带参行为单元

> **只要游戏里有「技能 / 道具 / buff / 敌人行为」这类概念，重复就是必然的。**

本轮做**带参数的可复用规则组**；**配方就是它的预设**（§4.3），不是第二套机制：

```
定义：技能「火球」(伤害, 冷却, 特效)
使用：施放 火球(30, 2秒, 爆炸)
```

三条约束，用来守住 I2 和 I3：

| # | 约束 |
|---|---|
| **B1** | 定义体**就是普通规则行**，能展开看、能改——不是黑盒 |
| **B2** | **不允许递归、不允许任意控制流**（§3.4 真封顶），保住可校验与可被 AI 读懂 |
| **B3** | 参数是**有 schema 的**，因此 AI 能填、约束层能校验、详情面板能自动生成控件 |

敌人 AI 用同一套东西表达（「巡逻」「追击」「远程攻击」都是行为单元），**不另起一套行为树**。

#### 3 · 运行期状态存取（存进度）

§3.5 原来写着「运行时存档不做，格式由游戏自己定义」。**那条在技术上成立，在产品上说不通**——
任何超过十分钟的游戏都要存进度，不提供就等于用户只能做几分钟的小品。

本轮提供的是**两个事件表动作 + 一条规则**：

```
存进度(槽位)    读进度(槽位)
```

- 存什么由游戏自己声明：勾选要持久化的全局变量与实体状态
- **实体 id 必须稳定**，否则读档会错位——与 I11 的标识符稳定性同源
- 封顶：不做云存档、不做多存档槽的管理界面（§3.4）

#### 4 · 数据表（决策 32，v16 新增）

> **行为单元解决了「结构」的重复，没解决「数值」的重复。**

§9 一直挂着「数值表达力够不够」，但那问的是**表达式**（伤害公式写不写得出来）。
真正缺的是**结构**：单位属性表、升级曲线、装备词条、掉落权重——
**几十上百行数值该放在哪、怎么编辑、怎么被规则引用。**

现在的答案只能是「堆全局变量」，而那在三个地方立刻破功：编辑（没有表格视图）、
AI（`describe` 出来是一堆无关联的变量名）、约束层（校验不了「每个兵种都要有攻速」）。

```
数据表「兵种」
  行 id     血量   攻击   攻速   造价
  步兵      100     8     1.0     50
  坦克      600    40     0.6    300

事件表里：生成 单位(兵种.坦克)   →   血量取自 兵种[坦克].血量
```

三条约束：

| # | 约束 | 为什么 |
|---|---|---|
| **T1** | 表是**内容包的一种形态**（决策 27），带 id 与版本 | 模板与模块要能各带自己的表；remix 时按依赖解析 |
| **T2** | 列**有 schema**，与组件 schema 同一套机制 | 详情面板自动生成、AI 能填、约束层能校验 |
| **T3** | 行 id **只增不改**（I11） | 事件表按行 id 引用；改一次 id，所有引用它的已发布作品变砖 |

**为什么现在就要定**：表的引用形式一旦进了快照，事后再改就撞 I11。
**实现可以分批**（决策 26）——本轮只做「具名表 + 定长列 + 按行 id 取值」，
公式列与外部表格同步留口。

#### 5 · 运行期动态集合（决策 37，v17 新增）

> **数据表是作者写的，静态；这一样是游戏跑起来之后自己增删的。**

数据表（概念 4）解决了「数值放在哪」，但它是**内容**——行 id 只增不改、随内容包分发。
而游戏运行时需要**可增删的集合**，现在无处安放：

| 集合 | 出现在 |
|---|---|
| 背包 / 容器 | 塞尔达、艾尔登、TPS |
| 物品栏与信使栏 | **Dota 2** |
| 生产队列、编队、选中组 | 红警、星际、魔兽 |
| 任务列表、已解锁清单 | 全部 |

**三款以上、且跨两个簇都需要**（决策 39 的判据），所以进内核。

现在手里的三样都不够：数据表是静态内容；全局变量是标量；事件表的选中集**每条规则用完即弃**（[adr-002](adr-002-eventsheet-eval.md) P3）。

本轮做两种形态 + 四个动作：

```
有序集合：背包 = [剑, 药水, 药水]      加入 / 移除 / 取第 N 个 / 计数
键值表：  已解锁 = {神庙A: true, ...}   设置 / 删除 / 取值 / 是否存在
```

三条约束：

| # | 约束 | 为什么 |
|---|---|---|
| **C1** | 元素是**标量或实体引用**，不允许任意嵌套结构 | 保住可序列化、可 diff、可被约束层校验（同 B2 的理由） |
| **C2** | **可声明持久化**，与概念 3 的存进度共用同一套声明机制 | 背包不能存 = 存档没意义 |
| **C3** | 集合的**迭代顺序是稳定的**（插入序） | 确定性（决策 29、[adr-002](adr-002-eventsheet-eval.md) D1）；顺序不稳定则 lockstep 立刻不同步 |

**封顶**：不做排序、过滤、嵌套查询——那会把它变成一门查询语言，撞 §3.4 的「任意控制流」封顶。

**为什么现在就要定**：它要进存档（概念 3），格式一旦落盘就撞 I11——**和数据表是同一个理由**。

## 五 · 功能大纲

> **能力清单的读者友好版**：[architecture-outline.md](architecture-outline.md) §四 —— 按九个子系统分组，每项写清做到哪儿

### 5.1 内核

**世界** — 实体 / 组件表 / 原型查询 / 组件 schema 注册；系统注册与调度（固定步长 + 帧步长）；序列化（确定性、版本化、可 diff）；快照与回滚。

**变更** — Action Registry（id / JSON Schema 参数 / 前置条件 / 影响域 / 可逆性 / describe）；撤销栈 + 变更日志；`listAvailableActions(context)` 情境级自省。

**事件表** — 数据模型 `规则[] = { 条件行[], 动作行[], 分组, 启用 }`，有序，全部是普通组件数据；条件 / 动作注册表（带 schema、**人话模板串**、**常规 / 触发标记**）；播放期按 [adr-002](adr-002-eventsheet-eval.md) 的语义求值（**全表自上而下 + 触发即时插入**，实体集按种类逐条收窄、子事件只继承不回写、顶层规则之间不传递）；全部编辑动作 Action 化；**多层子事件 + 参数位简单算术**（§3.4）；**配方库 + 用户可把自己的规则组存成配方**；第一批条件动作（碰到 / 进入范围 / 被点击 / **输入意图被按下**（I12）/ 定时 / 开局 / 数值比较 / 概率；移动 / 跳跃 / 朝向 / 生成 / 销毁 / 改属性 / **播动画** / **播音效** / **放特效** / 计分 / 等待 / UI 提示）。

**呈现** — kind 注册表（声明碰撞体、占地尺寸、可用动画状态）；皮肤包（一个工程一个当前皮肤，可覆盖到单个实体）；模型按插槽适配；动画状态缺失回退 + warning；约束「皮肤包完整性」。

**空间与物理** — Transform 层级（是组件，不是场景图）；空间索引（网格哈希 / BVH）；射线拾取、框选；**Rapier 刚体 + 碰撞 + 空间查询 + 固定与铰链关节**（决策 33；不做其余关节、马达、布娃娃、软体）。事件表要有「连接 / 断开」两个动作——**举起放下、磁力吸附、可组装机关全靠它**。

**分块与流式加载**（决策 30）— 场景内按**块**组织；实体随块**加载与卸载**；序列化**按块存取**（工程存档与快照都是）。
三条纪律，缺一条流式就会和确定性打架：

| # | 纪律 |
|---|---|
| **S1** | **加载顺序不得影响模拟结果**——块的加载是呈现层的事件，不是玩法事件 |
| **S2** | 玩法需要的**最小状态常驻**（例如远处敌人的存活与计时），只有**表现**随块进出 |
| **S3** | 卸载与重载后，**同一段输入必须得到同一结果**（闸门 A 的断言范围覆盖它） |

**本轮做**：分块 + 按需加载卸载 + 按块序列化。**留口后加**：LOD 层级、impostor、地形分块 mesh 简化。

**播放期的选择与指令**（附录 A.9）— 游戏内点选、框选、编队、对选中集下达指令（移动 / 攻击 / 跟随 / 停止），全部是条件与动作。
**这与编辑期的框选是两套东西**：那套服务编辑，这套是玩法能力。MOBA、RTS、战棋、任何「指挥一群单位」的玩法都要。

**播放期的放置与建造** — 玩家在游戏里放下一个东西：位置合法性校验、消耗资源、放置预览、可撤销。
**红警 / 星际 / 魔兽的建造与塔防的放塔是同一件事**（v17：判据源换成目标游戏后，它从「塔防要」变成「三款 RTS + 塔防都要」）。

**动画事件** — 在 clip 的时间点上打标记，触发事件表（开 / 关攻击判定盒、可取消后摇、脚步、特效点）。
没有它，动作与魂类的战斗手感无从谈起。标记随**皮肤包**走（语义状态 → clip → 时间标记），不进玩法层（I9）。

**场景与流程**（§4.7）— 多场景（各自可编辑可试玩）；流程数据（场景顺序与切换条件）；全局状态与场景内状态的分界；界面页（标题 / 暂停 / 背包 / 对话 / 结算）。

**行为单元**（§4.7）— 带参数、有 schema 的可复用规则组；定义体即普通规则行；不允许递归与任意控制流；技能 / 道具 / buff / 敌人 AI 全部用它表达。

**运行期状态**（§4.7）— `存进度(槽位)` / `读进度(槽位)` 两个事件表动作；游戏自己声明要持久化什么；实体 id 稳定性由内核保证。**等待队列（含实体集快照与剩余时间）属于运行期状态，必须可序列化**（[adr-002](adr-002-eventsheet-eval.md) W2）——技能冷却与波次间隔全是等待，漏了它读档就丢。

**数据表**（§4.7、决策 32）— 具名表 + 有 schema 的列 + 按行 id 取值；表是内容包的一种形态；行 id 只增不改（I11）；事件表与行为单元可引用；详情面板按列 schema 自动生成表格视图。

**运行期动态集合**（§4.7、决策 37）— 有序集合与键值表；加入 / 移除 / 取值 / 计数四类动作；元素限标量与实体引用；插入序稳定（确定性）；可声明持久化，与存进度共用同一套声明。

**寻路**（决策 38）— 群体寻路 + 局部避让；查询接口与实现分离（退役条件：500 单位下掉帧且优化无果 → 换流场，**接口不变**）。**必须是确定性的**——寻路结果进玩法状态，走 [adr-002](adr-002-eventsheet-eval.md) D1 的稳定迭代顺序。

**视野与战争迷雾**（决策 38）— 按阵营的视野计算与迷雾状态；事件表可查询「X 是否可见」。**迷雾是玩法状态不是渲染效果**——它决定 AI 能不能看到你，因此进玩法层、参与断言。

**动画**（决策 36 档 2）— 状态机（状态是玩法数据，转移由事件表驱动）+ 混合 + **root motion**（位移曲线烘焙成玩法量、归 kind，见 §4.4）+ 交叉淡化 + 动画事件。**不做 IK / 动作匹配 / 上下半身分层**。

**技能目标选择** — 点地 / 点单位 / 方向 / 范围指示器，是行为单元的参数形态（B3 的 schema 扩展）。Dota 的技能、艾尔登的锁定、RTS 的指令共用同一套。

**输入**（I12、决策 24）— **输入意图**注册表（跳跃 / 移动 / 确认 / 取消…，由内核与模块注册）+ **设备绑定表**（键鼠 / 触屏 / 手柄，一张可换的映射表，和皮肤包同一个模式）。事件表只认意图，不认设备。

**宿主能力抽象**（决策 24 P3）— 全屏、指针锁定、URL、存储、文件读写各一层薄接口；浏览器是其中一种实现，套壳时换实现即可。

**渲染桥** — 组件 + 当前皮肤包 → three.js 增量同步；**相机档位**（受限俯视 / **肩后跟随** / 第一人称 / 自由飞行，v17 起默认不再是受限俯视）+ 跟随平滑 + 震动 + 锁定目标；帧循环、可见性剔除。（触屏与自适应画布随移动端一并推后。）

**视听**（决策 23，封顶见 §3.4）—
动画：glTF clip + **交叉淡化过渡**，状态由事件表与皮肤包驱动；
材质与光照：参数面板 + 若干套环境与光照预设；
后处理：几个预设档位；
特效：一组预制粒子（命中 / 爆炸 / 拾取 / 尘土 / 拖尾），事件表可触发；
音频：音效与背景音乐的播放 / 音量 / 循环 / 停止，全部是事件表动作。

**游戏内 UI** — DOM overlay：跟随实体的屏幕锚点 + 生命周期 + **一组预制件**（血条 / 计分 / 计时 / 提示 / 胜负画面）。不做控件系统。

**素材** — 内置风格中性、可互相搭配的素材库（随编辑器分发）；glTF 导入同等优先；文生 3D 作为可插拔 provider。

**分享与账号** — 发布（工程 → 只读快照 → **注册 / 登录** → 上传 → 换回链接，决策 28）；玩（打开链接只加载播放期，**不需要账号**）；remix（拉回本地新建工程，**不需要账号**）。
后端只存**已发布快照 + 最小账号信息**，不存正在编辑的工程。快照带内容哈希、引擎版本号与**作者 id**（I11）。
账号形态：**优先 OAuth，不自建密码体系**；作品可归属、可删除；一个举报入口 + 管理员下架能力。
**不做**：个人主页、关注、私信、自动审核。

**数据安全底线**（§3.6.3 / 3.6.4）— 自动保存；导出自包含工程文件；overlay 一律 `textContent`；导入与快照解析设上限并优雅失败。

**试飞台** — headless runner（加载 → 执行 Action 序列 → 断言 → 报告）；确定性（清除 `new Date()` / 随机数对世界状态的渗透）。

**AI 基础设施** — `describe(scope, detail)` 语义 LOD（组件与事件表都要实现）；约束层（谓词 + 结构化失败反馈 + 修复建议）。详见 [ai-native-engine.md](ai-native-engine.md)。

### 5.4 AI 作者接口

| 顺序 | 能力 | 说明 |
|---|---|---|
| 1 | **单步指令** | 一句话 → 一条 Action，预览后确认 |
| 2 | **换皮 / 配皮肤** | 只改皮肤包映射，不碰任何规则（I9）。作用域最小、错了一眼看得出 |
| 3 | **多步变更集** | N 条 Action → 半透明预览 + 清单 → 整体接受 / 逐条剔除 → 合成一条撤销 |
| 4 | **生成规则行** | 产出 Action 序列（挑配方 + 填参优先），可见、可手改、可逐行 diff |
| 5 | **内联建议** | 选中物体 → 1–2 条可点击的建议 |

#### AI 参与度的三档（决策 40，v20 修订）

> **五根支柱本来就是 agent 的闭环**：`describe` 感知 · `listAvailableActions` 知道能做什么 ·
> `apply` 行动 · 约束层给结构反馈 · headless 提供可重复的行为 oracle。
> v20 补上的不是更多模型能力，而是**引擎拥有的控制协议**：谁批准、谁提交、谁判定通过、何时必须停止。

| 档 | 能力 | 状态 |
|---|---|---|
| **档 1** | 上表五种形态；一次生成 Action 变更集，预览后由人接受；可运行已给定的 TestSpec 并报告证据 | **本轮做**（阶段一接单步，阶段三补齐） |
| **档 2** | **验证驱动的自主循环**：批准 `PlanContract` 后，按步骤执行 Action 事务；结构 / 行为 / 体验三层验证；失败进入有界修复；全过程可见、可停、可回到任一通过 checkpoint、可只接受已通过的前半段 | **本轮做**（阶段三，见 [ADR-003](adr-003-verified-agent-loop.md)） |
| **档 3** | **AI 造零件**：AI 用 JS 实现新的条件与动作，扩展编辑器自身的能力面 | **留口** |

**档 1 与档 2 的差别不是规模，是控制权**：档 1 是一次性 batch（吐 N 条 → 一次 review）；
档 2 是持久运行（计划 → 执行一步 → 验证 → 修复或提交）。长任务不能靠 50 条 Action 的复选框管理，
也不能让模型在同一上下文里自写、自验、自称成功。

**档 2 的七项硬协议**（字段与状态机见 [ADR-003](adr-003-verified-agent-loop.md)）：

| # | 协议 | 硬边界 |
|---|---|---|
| **P1 计划契约** | `PlanContract` 声明 `baseRevision`、作用域、步骤依赖、允许的 Action、预期影响、TestSpec 与预算；Markdown 只是视图 | 计划变更后旧批准立即失效；复杂任务未经批准不得执行 |
| **P2 步骤事务** | 每步在候选分支 `preview`，hard oracle 全过才 `commit` checkpoint，失败 `abort` | 步骤内全有或全无；不得提交失败步骤的半批 Action |
| **P3 分层验证** | V1 schema / 前置条件 / 约束；V2 确定性 headless / 输入轨迹 / 状态断言；V3 日志 / 截图 / 体验观察 | V3 与模型自评不能覆盖 V1 / V2 的 hard 失败 |
| **P4 角色隔离** | planner / executor / verifier 使用隔离的上下文与权限；可由同一模型承担 | verifier 不能继承 executor 的「已经完成」结论，也不能改 hard TestSpec |
| **P5 证据账本** | `StepReceipt` + `EvidenceLedger` 记录真实 diff、测试、输入、seed、日志、截图、provider、成本与判定 | 自然语言总结不能替代可重放证据 |
| **P6 有界修复** | 每轮先写失败签名、原因假设、最小修复集与回归范围 | 重复失败、越界、削弱测试、缺少原语、冲突或超预算立即停 |
| **P7 引擎控制** | 状态机、审批、权限、步数 / 时间 / 费用预算与中断信号都在引擎侧 | 模型只能请求状态转换，不能自行提交、批准或延长预算 |

三个稳定入口仍保持**无状态、可多轮调用**；运行状态属于独立的 `Run`，不能藏进 provider 会话。
多 agent 并发编辑与合并仍不做；角色隔离是权限边界，不是并发要求。

**档 3 的一条硬约束现在就写死**：

> **AI 写的 JS 条件动作不得自动注册。**
> 必须过 §7.1 的确定性沙箱静态检查（J1–J3）+ 一次 headless 断言，且在 registry 里**标明来源**。
> 理由是 **I11**：一个条件动作的 id 一旦被作品引用就冻结了——**AI 随手造一个，就等于永久多了一份迁移负担**。

**这是能力天花板的真实位置**：档 1、档 2 下 **AI 能组装，不能造零件**；
超出现有条件动作库的需求，得由人先写零件。

**必须一等对待的非功能项**：延迟与费用预算、失败兜底（AI 不可用时编辑器完全可用）、
错误通过率（hard 负例不得被判通过）、可解释（说清改了什么、为什么）、可恢复（失败退回最近通过 checkpoint 的距离恒为 0）、
离线（没有 AI 也能用模板与配方做事）。

> **v17 加重**：决策 35 把门槛交给了 AI 与教程，**AI 的可用性因此从「产品卖点」变成「承重结构」**。
> 上面四条非功能项现在与功能同级——尤其「失败兜底」：AI 挂掉时，教程与配方必须能独立扛住门槛。

### 5.5 模型接入（决策 21）

> **用户能填自己的模型，而且填起来不难。**
> 内置 AI 开箱即用；但从第一天就假设「用户会换成自己的」。

#### 供应商适配层

一个 provider 只需实现三件事：**发一次请求、拿回文本或 JSON、报告自己的能力**。

| 形态 | 说明 |
|---|---|
| **OpenAI 兼容端点**（base URL + key + 模型名） | **这一条覆盖绝大多数场景**：各家云服务、聚合网关、自建代理，都是它 |
| Anthropic / Gemini 原生协议 | 各写一个适配器，因为请求格式不同 |
| **本地模型**（Ollama / LM Studio 等） | 也是 OpenAI 兼容端点，零成本、数据不出机器 |

**新增一家 = 加一个适配器**，其余全部不动（I5 的一次应用）。

#### 能力契约与降级（I10 的执行点）

引擎声明**它需要什么**，provider 声明**它有什么**，缺的部分自动降级：

| 能力 | 有的时候 | 没有的时候（降级） |
|---|---|---|
| 结构化输出 / 约束解码 | 直接按 Action 的 JSON Schema 出参，语法错误为零 | prompt 里贴 schema + 输出后校验 + 失败重试（最多 N 次） |
| 工具调用 | 三个入口做成 tool（`describe` / `listAvailableActions` / `apply`） | 退化为单轮 JSON 协议：一次给上下文，一次要结果 |
| 长上下文 | 一次给更多 describe 结果 | **渐进披露本来就按需取**，影响很小（见[附录 A.7](#a7-决策-21为什么接各种模型是可行的)） |
| 流式输出 | 边生成边显示预览 | 转圈等待，功能不减 |

**底线**：只要模型能「读一段文字、按要求吐一段 JSON」，编辑器的 AI 功能就应该可用——**只是慢一点、重试多一点**。

#### 设置界面

**v17：目标用户配得来 base URL 和 key**，所以这一节的门槛论证不再必要。
但下面几条**全部保留**——它们对专业用户同样成立，只是理由从「不写代码的人也要能配好」
换成「**配置成本应该低到不值得抱怨**」：

- **预设列表** + 一个「自定义端点」——不必知道什么是 base URL 也能开始
- 填完有一个**「测试连接」**按钮：报告能否连通、探测到哪些能力、大概多快
- **每类任务可以选不同模型**（够用的两档就好：快 / 强）。换皮、单步指令用快的；生成规则行用强的
- **用量与花费可见**：BYOK 是用户自己付钱，看不到花费就不敢用
- **隐私说明写在设置页上**，不藏进文档：说清哪些内容会被发出去（`describe` 的结果、当前选中的东西、事件表片段），以及**本地模型可以让这一切不出机器**

#### 密钥与安全

- 桌面外壳：密钥存在本地
- 网页版：**走内置代理**，不在浏览器里明文存 key
- 引擎**不用用户的 key 做用户没要求的事**（不做后台预热、不做遥测调用）

#### 边界（防膨胀）

不做模型路由 / 自动选模、不做 RAG 与向量库、不做微调、不做多模型投票、**不引入通用 agent 框架作依赖**。
**适配层就是「一个函数 + 一张能力表」**，本轮不许长成子系统。

> **v18 澄清**：最后一条说的是**不把 LangChain 一类通用框架变成依赖**，
> **不是禁止自主循环**。决策 40 的档 2 由引擎状态机编排三个稳定入口，与本节边界不冲突——
> 恰恰相反，**渐进披露与三入口就是为了让循环的上下文成本不随 Action 数量增长**（[A.7](#a7-决策-21为什么接各种模型是可行的)）。

## 六 · 路线与闸门

> 阶段之间是硬依赖。**不含工期承诺。**
>
> **v17 的总顺序：先自用 → 再验证 → 再开放。**
> 第一个里程碑不是「别人能用」，是**你能用它做出你想做的游戏**。
> 分享、账号、后端、面向新手的一切**整体推到阶段四「开放」**。
>
> **数据模型先行**：§4.7 五个概念的数据模型**阶段二就定死**，实现分批。
> 先定数据模型是为了不撞 I11——这五样一旦发布后再改，已有作品会全废。
>
> **比它更先的只有一样**：事件表的**求值语义**，阶段零定稿（决策 31、[adr-002](adr-002-eventsheet-eval.md)）。
> 数据模型改错还有迁移链，求值语义改错**迁移链救不了**（§3.6.5）。

### 阶段零 · 工程地基 + 三份协议推演

引入 package.json + 打包器；现有 three CDN importmap 迁进构建。
它挡着 ECS / Rapier / glTF 三件事，不先做，阶段一第一天就会撞上。

**并行做完一件纸面工作：事件表求值语义定稿**（决策 31、[adr-002](adr-002-eventsheet-eval.md)）。
它不写代码、不依赖打包器，但**阶段一的 Action 层、序列化、试飞台断言全部受它约束**。

**另行走通 [ADR-003](adr-003-verified-agent-loop.md) 的三个控制协议样例。** 它不像求值语义那样不可迁移，
所以不并入闸门 O；但 `baseRevision`、步骤事务、TestSpec 与 checkpoint 字段必须在阶段一 Action / 快照格式落地前定形，
否则阶段三会反过来重写撤销、序列化与试飞台。

**同时走通 [ADR-004](adr-004-evidence-governed-evolution.md) 的三个治理回放。** 它先于所有后续 AI 指挥任务：
回放 v17/v19 漂移、ADR-002 隐含语义和协议自我挑战；建立治理基准集，验证 AI 能主动发现用户没有指出的关键决策，
并能拒绝无收益的流程膨胀。它不冻结具体检查表，只冻结权限、证据与采用边界。

- **闸门 O（纸面）**：ADR-002 的三个手工样例（塔防选目标 / 跳跃缓冲 / RTS 指令）逐条推演，
  结果与「读这段规则会预期什么」一致。**过了就按 I11 冻结**，此后只许改实现不许改语义
- **治理准入 G0（纸面）**：ADR-004 的 G1–G3 全部发现植入的关键遗漏、越权修改为 0；
  在这之前可以做打包器和人工 spike，但 AI 不得把新的不可逆方案写成已定结论

### 阶段一 · 内核地基

ECS 内核 + 封装层 + **按块序列化** + 快照；Action Registry + 撤销 + 日志 +
**步骤事务底座**（`baseRevision` / `idempotencyKey` / preview / commit / abort / checkpoint / `StepReceipt`）；
**试飞台（headless runner + 确定性 + TestSpec）**；渲染桥 + Transform + 拾取 + 空间索引 +
**分块与流式加载**（决策 30）；编辑器改造（大纲 / 详情 / gizmo / 多选，全部对 ECS 通用）；
**阶段末接最小 AI（单步指令）**——验证通道形状和事务回执，不是模型能力。

- **闸门 A**（四条）：
  1. 手写一段 Action 序列（JSON），headless 执行后与 GUI 手动操作得到的状态**逐字节一致**；存读档、撤销、重放全部通过
  2. **块卸载再重载后，同一段输入得到同一结果**（决策 30 的 S3）
  3. **Rapier 的确定性 spike 通过**——同一输入在两台不同机器上逐帧一致。
     **不通过就换物理库，不放宽决策 29**
  4. **Action 步骤事务负例通过**：过期 `baseRevision` 不覆盖、同一 `idempotencyKey` 不重复执行、
     步骤中途失败不污染主工程、回到最近通过 checkpoint 不需要补偿 Action
- **闸门 B（纸面）**：城市迁移演练——不写代码，逐项验证路 / 地形的数据结构与命令能否用内核概念表达。**过不了就改内核**

### 阶段二 · 事件表 + RTS 模板

事件表数据模型 + 列表编辑器 + 按 [adr-002](adr-002-eventsheet-eval.md) 求值；第一批条件动作库（**广度由 RTS 倒推**）；配方库；
**§4.7 五个概念的数据模型定死**（场景与流程结构、行为单元 schema、可持久化状态声明、数据表的表与列 schema、**动态集合的两种形态**），
**实现只做最小**：两个场景能切换、一个带参行为单元能定义与调用、存读进度能跑通、一张数据表能被规则引用、**一个背包能增删并存档**；
播放模式 = 快照沙箱；物理 + 关节 + glTF 导入 + 内置素材库；皮肤包机制 + 编辑面板 + 两套皮肤；
**群体寻路 + 视野迷雾**（决策 38）；**播放期选择与指令 + 建造**；**技能目标选择**；
**视听下限一套**（音频、预制粒子、材质与光照预设、后处理档位——决策 23）；游戏内 UI overlay 与预制件；
**约束层的机制**（谓词注册 + 结构化失败反馈 + 面板显示）——闸门 C.5 的皮肤包完整性、§1.3 主循环的当场提示都依赖它，**不能等到阶段三**；
**平台跳跃脚手架**（最快拿到可玩闭环，不作交付模板），随后 **RTS 模板**；
**导出自包含工程文件**；**脚本化试玩 + TestSpec + 输入意图轨迹 + 状态断言 + 证据片段**；
V3 首批观测接口（日志、截图引用、真实键鼠 / 输入意图，不允许用直接传送替代被测输入链）；
**教程系统的机制 + 已交付能力的教程条目**（决策 35）。

- **闸门 C**（五条，v17 从七条改来）：
  1. **RTS 模板可玩通一局**（采集 → 造兵 → 交战 → 分胜负），**全部逻辑由事件表与行为单元表达，没有一行专为它写的硬编码 JS**
  2. 平台跳跃脚手架同样成立，且两者复用同一内核与同一套条件动作库的公共部分
  3. 同一局能在 headless 里由脚本驱动跑完并断言结果，**含 1000 单位规模下不掉帧**
  4. **导出的工程文件能在另一台机器上打开并继续改**（v17 替代原「发链接给陌生人」）
  5. **换皮不变**：换一套皮肤包，**一行规则不改**，headless 同输入下**玩法状态**逐字节一致
- **原第 5 条「配方可用性」与第 7 条「成品感 / 手机可玩」的处置**：
  前者改为**教程可用性**，并入阶段三的闸门 D；后者随移动端一并推后，
  **但决策 23 的视听下限本身不砍**（§3.4 各项照做，只是不再有「手机上打开」这个判据）

### 阶段三 · AI 作者接口 + 验证驱动控制循环

describe 层；**约束层接到 AI 上**（机制阶段二已建，这里加的是「作为验证器与修复信号」那一半）；
单步 → 换皮 → 多步 → 生成规则行 →（内联建议）；**供应商适配层 + 能力探测与降级 + 设置界面**（决策 21）；
并按 [ADR-003](adr-003-verified-agent-loop.md) 落地 `PlanContract` 编辑器、Action 步骤事务、
orchestrator 状态机、三层 verifier、`EvidenceLedger` 与有界 repair policy。

- **闸门 D**（六条；D.4 含五个不可拆的子判据）：
  1. 一句话生成一个可玩的关卡**及其逻辑**；复杂任务先生成可编辑 `PlanContract`，批准前零变更；简单任务仍可直接预览 Action 变更集
  2. **生成的规则行能被手动继续修改**（I3 的验收点）
  3. 端到端时间、Action 数、修复次数与模型费用有明确预算；超时、超支、越界与冲突都有可恢复兜底
  4. **验证驱动自主循环通过完整负例套件**：
     - **D.4a 计划与审批**：计划可编辑、可重排、可删除步骤；批准绑定版本，计划变化后旧批准失效
     - **D.4b 事务与恢复**：每步失败不污染主工程；可停止、恢复到任一通过 checkpoint、只接受已通过的前半段；重复请求不重复执行
     - **D.4c 独立验证**：V1 结构 + V2 确定性行为决定 hard 通过，V3 提供体验证据；人工植入的 hard 失败错误通过率为 0
     - **D.4d 有界修复**：修复不得删改 hard TestSpec；同一失败重复、缺少原语、越界或超预算时必停并交还证据
     - **D.4e 证据可重放**：每步 diff、约束、输入轨迹、seed、状态断言、日志、截图、provider 与预算形成 `EvidenceLedger`，另一进程可重放得到同一 hard 判定
  5. **教程可用性**（v17 换掉原「简易模式下全程可完成」）：一个懂引擎、但没用过本编辑器的人，
     **只靠内置教程与 AI**，能走通主循环并改出一个与模板明显不同的关卡。**这是决策 35 的验收点**
  6. **换一家模型仍可用**：把默认模型换成另一家（含一个**无结构化输出、无工具调用**的模型
     与一个**本地模型**），D.1–D.5 仍然通过；只允许更慢、重试更多，事务、权限与 hard 判定不得变化（I10 与决策 21 的验收点）

  且全部逻辑由事件表与行为单元表达，**没有一行专门为它写的硬编码 JS**
  （用 JS 实现**通用的**条件与动作不算——那是决策 6 的正常路径；
  **算不算的判据是：这段 JS 能不能被另一个模板复用**）。

### 阶段四 · 开放（v17 重立，原「第三个模板」出局）

  2. 加入**第三个模板**（任选一个八款之外的玩法）时，内核**没有新增领域概念**（[§5.2](#52-内核归属论证) 表格不新增行）。

## 七 · 模块契约与迭代纪律

> 目标：让**单个模块的改动代价低到可以频繁失败**。
> 可迁移的只有两条：**接口冻结、内部自由演进**；**敢整块丢掉**。
> 不可迁移的是「提前为所有模块设计插件接口」——接口该长什么样，要造完第一个才知道。

**好消息**：ECS + Action + 事件表本身就是模块化底座，不需要另起炉灶。

| 已选架构 | 天然给出的边界 |
|---|---|
| ECS | 模块 = 一组组件 + 一组系统，系统之间只通过组件通信 |
| Action 层 | 模块的对外能力 = 它注册的 Action，可枚举、带影响域 |
| 条件动作库 | 模块给用户的能力，同样可枚举、可 describe |
| 皮肤包 | 模块的呈现层，可整套替换 |
| 约束层 | 模块的正确性契约，可独立验证 |

### 7.1 模块契约

每个模块一个声明文件，启动时校验，越界即报错：

```
components:   组件类型 + schema
actions:      注册的 Action
rules:        注册的条件与动作
kinds:        语义种类 + 玩法量（碰撞体、占地、可用动画状态）
skins:        提供的皮肤包 + 要求的视觉插槽清单
constraints:  声明的约束
systems:      挂载的系统 + 调度阶段
panels:       注入的编辑器面板
templates:    提供的模板
depends:      依赖的其他模块（DAG，禁止循环）
```

**禁止**：直接 import 另一个模块的内部实现、直接读写不属于自己的组件表、绕过 Action 层改编辑期状态、直接 import 第三方 ECS 库、**在事件表或玩法组件里引用具体美术资源**（I9）、**在条件与动作的实现里触碰时间与随机源**（见下）。

#### 确定性沙箱（决策 29 的执行点，v16 补）

决策 29 把逐帧确定性升为硬要求，但**一直缺一个执行点**：决策 6 允许用 JS 实现条件与动作，
而 `Math.random()` 或 `Date.now()` 只要出现一次，lockstep 与 headless 断言**同时废掉**——
且失败是随机的、极难排查。

| # | 约束 |
|---|---|
| **J1** | 条件与动作的 JS 实现跑在**受限环境**：禁 `Date` / `Math.random` / `performance` / 网络 / 存储 / DOM |
| **J2** | 内核注入 `rng`（带种子）与 `tick`；要随机、要时间，只能从这里拿 |
| **J3** | 违反在**注册时**就报错，不等到运行期——静态扫一遍实现体即可 |

同一条纪律也适用于内核自己：[GameClock](../../js/sim/GameClock.js) 的 `new Date()` 与
[core/project.js](../../js/core/project.js) 的 `randomUUID()` 是存量里已知的两处渗透（ai-native-engine.md 支柱五）。

### 7.2 三条纪律

| 机制 | 内容 |
|---|---|
| **变化轴声明** | 每个模块回答「我预期未来在哪几个方向上变」。价值是反向的——它同时说明哪些地方**不打算变**，因此现在**不要**为它做抽象 |
| **退役条件** | 每个模块写明「什么情况下该整个丢掉」。大多数项目死于舍不得丢 |
| **三次法则** | 不要在第二个用例出现之前抽象。第一次写死，第二次复制，第三次才抽象 |

**已写下的退役条件**：

- 寻路：500 单位下掉帧且优化无果 → 换流场，**查询接口不变**
- 物理：Rapier 体积或确定性不达标 → 换库，**空间查询接口不变**
- 事件表：若模板逻辑写不出来必须硬编码 JS → **加受限原语，不退回节点图**
- 城市模块：迁移工作量超预算 → 放弃（已降为可选）
- ECS 库：spike 的确定性测试不过 → 换库或自研；**封装层保证换库代价限制在约 800 行内**

**项目级的退役条件**（同一条纪律，也该对项目自己生效）——**v17 反转**：

> 原文是「若普通人改不出关卡 → 转向面向有经验创作者」。
> **v17 之后那已经是起点，不是退路**，所以这条要换一个方向写。

新的两条：

| # | 触发条件 | 执行什么 |
|---|---|---|
| **P-1** | 闸门 F 通过后，**开放阶段（阶段四）迟迟无法开工，或开工后无人使用** | **承认它是个人引擎**，停止在分享 / 账号 / 新手视图上继续投入，把资源转回引擎能力本身。这不是失败，是把「三者都想要」收敛成「先自用」那一项——它本来就是第一优先 |
| **P-2** | 闸门 D.5（教程可用性）连续两轮不过 | 说明**决策 35「门槛交给 AI 与教程」不成立**。此时要回头重估决策 12 的取消——面向新手的裁剪视图（I8 的留口）可能得兑现，而不是继续加教程 |

**风险 6′ 的对应**：「先自用」的代价是架构可能长成只服务一个人的形状。
P-1 不是为了预防它，是为了**在它发生时不自欺**。

提前写下来，到时候是执行判断，不是情感决策。

### 7.3 迭代速度来自试飞台，不是模块划分

headless runner（不开界面跑完整场景）+ 确定性（失败可复现）+ 约束层（不用人看就知道对不对）。

判据：**改完内核，几秒内就能知道所有模板有没有被搞坏。**

### 7.4 决策发现与证据演化（决策 42）

研发 AI 的入口不是直接写计划，而是先按 [ADR-004](adr-004-evidence-governed-evolution.md) 建立：

```text
TaskContract
  → 十二面 DecisionCoverage + 负空间扫描
  → 若涉及规则 / 表达式 / 状态机：条件式逻辑探针
  → 未知进入 §9 / 高风险触发 DecisionChallenge
  → 可逆实验与独立质疑
  → 证据支持的 PlanContract / 实现
  → evidence package
  → champion 保持或被 challenger 取代
```

| 层 | 不允许 AI 静默改变 | 允许怎样进化 |
|---|---|---|
| **意图与裁决** | 一句话定义、不变量、hard gate、权限、历史 | AI 可挑战并提交证据，项目所有者批准后走决策修订 |
| **计划与实现** | 已批准 scope、hard oracle、冻结语义 | 在适配层、候选分支、feature flag 或 shadow mode 中比较 challenger |
| **治理机制** | L0–L1 的人类保留权、证据只增不改 | 在历史漏判集 + 新植入案例上影子运行；漏判下降且审阅负担可控才升级 |

**高风险未知只阻塞依赖它的不可逆提交，不阻塞整个项目。** 当前最佳假设仍可用于可逆工作，
但必须写明失效条件、证据要求和回退点。方案采用看证据，不看模型数量，也不要求项目所有者先识别技术错误。

条件式逻辑探针只在规则、表达式或状态机任务启用；它检查 AND / OR / NOT、`any` / `all` / `none`、
短路与副作用、运算符优先级，以及分支间实体集的可见性和传播。其他任务只记录“不适用”，不增加普适决策面。

**关于护城河（风险 10 的展开）**

不是「又一个通用引擎」——那条路拼不过 Godot。**v17 之后的位置是：AI 与人共用同一条编辑通道的 3D 引擎。**

- **与世界模型**（Genie 一类）的边界：它们交付**生成的体验**（一次性、不可寻址、改不了），本项目交付**可持续编辑的工程**
- **与 Nilo / Astrocade 的边界**：两家都在同一处让位——**产出用户改不动**（前者生成代码，后者黑盒）
- **与 Unity MCP / Godot AI 的边界**（v17 起这是最重要的一条）：它们是**外挂式**——
  文件是权威，AI 改完编辑器要重载、撤销栈丢失、人无法单独撤销 AI 的某一步。
  **本项目的 AI 通道是内生的**（[ai-native-engine.md](ai-native-engine.md) 问题定义）

**I1 + I3 仍是设计原则，但不再单独宣称市场独有。** Unity、Roblox 与 GDevelop 都已让 AI 直接改工程；
Clay 的差异化落在这两条原则的**可验证执行**：确定性 Action 事务、逐步证据、hard oracle、恒定恢复成本与供应商无关。

> **v17 换了押注（原文是 I2 + I3）。** 换的原因不是 I2 变得不重要——
> **恰恰相反：I2「逻辑是数据」现在是 I1 的前提**。逻辑一旦变成代码，
> AI 的产出就无法走 Action 层、无法逐行 diff、无法局部重试、无法单独撤销。
> 变的只是**理由**：从「普通人要读得懂」换成「**AI 通道要成立**」。
>
> 这也让决策 13（事件表而非节点图）站得更稳了——
> 原来那条论证的一半依赖「用户实际读不读得懂」这个未经验证的假设（风险 5），
> 现在它依赖的是「模型写有序行比写图可靠」与「逐行 diff」（[A.2](#a2-决策-13为什么是事件表不是节点图)），
> **两条都不依赖画像。**
>
> **v20 补充**：市场已经追上「AI 在编辑器里做事」这个表层。I1 + I3 的价值不减，
> 但护城河必须由 [ADR-003](adr-003-verified-agent-loop.md) 的控制协议兑现，而不是靠一句定位声明。

### A.2 决策 13：为什么是事件表，不是节点图

| 证据 | 说明 |
|---|---|
| Godot 删掉了节点式可视化脚本 | 5000 人调研中**仅 0.5%** 以它为主力。官方复盘：「一开始的路子就不对」 |
| Godot 的文档理由同样适用于 AI | 每个例子都要截图、维护不动——**AI 也得看图或看一堆坐标** |
| 非程序员做出成品靠事件表 | Construct / GDevelop 的条件-动作行；社区共识是它比 Blueprint 好懂得多 |
| Blueprint 的成功不可迁移 | 它证明「可视化能替代代码」，不证明「可视化能让普通人编程」——用户本质上是程序员 |

**AI 侧的增益（决定性的一条）**：

| | 节点图 | 事件表 |
|---|---|---|
| 形状 | 图（节点 + 连线 + **布局坐标**） | **有序的行** |
| 模型生成 | 图结构 + 空间推理，模型公认短板 | 写列表，模型最擅长 |
| diff | 图同构比较 | **逐行 diff** |
| 出错定位 | 「某条连线错了」 | 「第 7 行的条件不成立」 |

**成本收益**：不再需要画布、连线交互、自动布线、布局算法、缩放平移。

### A.3 决策 14：为什么分享不能再推

- **Astrocade** 8 个月 2000 万活跃、7.5 万游戏，核心机制就是分享与 remix
- **Rosebud** 编辑能力更强，规模小两个数量级

而对本项目它几乎免费：决策 7 已是「同一应用切播放模式」，分享 = 一个 URL + 只读播放。
**且 remix 与决策 9 是同一件事**——模板就是别人的作品。做了分享，模板库会自己长。

**v14 的补充（决策 28）**：发布这一步改为需要注册。
它不再「几乎免费」了——后端要担用户数据的责任，发布转化也会掉一截（§10 风险 13）。
换来的是**作品归属**：匿名发布的作品，日后做市场时认领不回来，而决策 27 说市场是长期目标。

### A.4 决策 15：城市迁移为什么降级

3200 行迁移 + 新旧对拍是巨大沉没成本；而它要证明的（内核能承载不同领域）用 3–4 个小模板证明更强也更便宜；顺带修掉「两个模板太像」。**闸门 B 的纸面演练保留**——它便宜，且是内核设计的真实压力测试。

### A.5 决策 18：为什么不是「表达力做到哪一档」

那个问法本身是错的。削表达力换易懂，结果一定是塔防写不出来、被迫硬编码 JS（违反闸门 C）。
正确做法是**表达力保持中等，门槛靠配方降**——不够用的人往下拆配方，学不会的人直接用配方，**两拨人用的是同一份材料**。

**v8 的补充**：同一个错误在别处又犯了一次——「嵌套只许一层、不许参数位算术」也是削表达力。
没有多层子事件，规则会横向铺开成一大片；没有参数位算术，伤害公式这类东西根本写不出来。
两者都已放开，封顶改设在**任意控制流、递归、完整表达式语言**（§3.4）。

**v11 的再次补充**：同一个错误犯了第三次——「不做真函数」也是削表达力。
四款 AAA 的压力测试里，Dota 精确地打在这一点上：**只要游戏里有技能，重复就是必然的**。
现已改为做**带参数的可复用行为单元**（§4.7），封顶只留递归与任意控制流。

### A.6 决策 20：原型来自自己的代码

[state/roadTypes.js](../../js/state/roadTypes.js) 开头的三条注释就是完整雏形：几何只认 widthUnits；主题是场景级呈现，换主题是一次设置变更；主题声明规则而非宽度表。v5 只是把它从模块私有实现上提为引擎级机制。

判据几乎不额外花钱——I7 的 headless runner 与确定性本来就在计划里，**v5 只是把它认领为「美术隔离」的强制执行点**。

### A.7 决策 21：为什么「接各种模型」是可行的

这件事在别的引擎里很难，在本项目里便宜，原因是**架构已经把对模型的要求压到了很低**：

| 已有的设计 | 对模型要求的影响 |
|---|---|
| 只暴露三个入口（`describe` / `listAvailableActions` / `apply`） | 不需要「一次塞几百个工具」，弱模型也不会被工具目录淹没 |
| **渐进披露**：按需返回 schema | 上下文需求小，**不需要长上下文模型** |
| Action params 是**可直接喂给模型的 JSON Schema 子集** | 有约束解码就用，没有就贴 schema + 校验重试，行为一致 |
| 产出是 **Action 序列**而不是整张图 / 整段代码 | 每步独立可校验，**弱模型的错误是局部的、可重试的**，不是整体失败 |
| **约束层**给结构化失败反馈 | 重试是收敛的，不是乱撞——这正是弱模型最需要的 |
| 优先**挑配方 + 填参** | 把「创作」降级为「选择 + 填空」，弱模型也能做对 |

**结论**：`I10` 不是额外负担，它是前面几条设计的**自然推论**。
真正要守的只有一条——**不要在任何地方偷偷依赖某一家的独有能力**。

### A.8 决策 23：为什么「不做」清单需要拆成两张

原来那张扁平的清单把两件不同的事混在一起：

| | 砍掉它影响什么 | 处理方式 |
|---|---|---|
| **引擎范围** | 影响引擎能长多大 | 可以砍，砍了不影响用户作品质量 |
| **作品质量** | 影响用户能做出什么水平的东西 | **不能砍，只能封顶** |

音频、动画过渡、特效、材质与光照、移动端可玩全部属于第二类，却被写进了第一类。
后果是自相矛盾：**决策 14 要求作品发给别人玩，而一个没声音、手机打不开的链接根本发不出去。**

正确的做法不是「做 / 不做」，是**「做到哪儿为止」**——每一项给一个明确的封顶。
封顶才是防膨胀该管的地方；一刀砍掉不叫克制，叫把问题推给用户。

### A.9 主流玩法压力测试

**先分清两种判定，它们的结论完全不同：**

| 判定标准 | 问的是什么 | 结论 |
|---|---|---|
| **成品判定** | 能不能做出那款游戏本身 | **都做不到**——但那是 300 人 × 5 年、竞技网络与运营的问题，不是编辑器功能问题 |
| **灰盒 MVP 判定** | **核心玩法循环**能不能跑通，几何体代替美术 | **六个里五个可做**，缺四项通用能力 |

第二个才是对编辑器功能的有效判据。

#### 灰盒 MVP 逐款结论（v12）

| 游戏 | 判定 | 卡在哪 |
|---|---|---|
| **Dota 2** | ✅ 可做（单人对 AI） | 选择与指令、视野迷雾 |
| **星际 / 红警** | ✅ 可做（小规模） | 选择与指令、播放期建造、迷雾；500 实体上限偏紧 |
| **艾尔登法环** | ✅ 可做（Boss 房） | 动画事件 |
| **塞尔达** | ✅ 可做（神庙式解谜 + 小区域） | 元素交互矩阵只能小规模；大地图靠缩小绕开 |
| **CS** | ⚠️ 只有单人打 bot | **竞技本体做不到**，见下 |

#### v16 的三款复核

v12 的判定过于乐观了两处，也漏测了一整类玩法。**复核结论写在这里，不改 v12 的原表**：

| 游戏 | v12 | v16 复核 | 差在哪 |
|---|---|---|---|
| **红警 / RTS** | ✅ | ✅ **判定成立，是三者中最契合的一类** | 但有两个未归属的卡点，见下 |
| **塞尔达** | ✅ | ⚠️ **原判偏乐观** | 磁力抓取、举起放下、组装机关全要**关节**，而关节原本整个划在留口——**没有关节，物理只是「会掉下去」，不是「物理即玩法」**。已由决策 33 补上最小集 |
| **刺客信条**（v12 未测） | — | ❌ **只到潜入原型** | 见下 |

**红警的两个卡点**（都不是能力缺失，是无归属）：

1. **寻路被砍进塔防模块**（§5.2）。塔防要的是固定路径，RTS 要的是**几十个单位的群体寻路 + 局部避让**，
   难度不是一个量级。MVP 用小地图 + 流场够，但**要单独排，现在无规格**
2. **500 同屏实体**：50 单位/方 + 建筑 + 投射物 + 特效，勉强够。文档原文「偏紧」是准的

**刺客信条为什么只到潜入原型**：能做的是一座小据点、几个带视野锥的守卫、蹲伏、暗杀触发、
沿预设点爬墙——**做不到的是这款游戏真正的产品：移动手感本身**。

| 需要什么 | 现状 |
|---|---|
| 跑酷 / 攀爬 / 边缘抓取 | 动画状态机、混合树、IK **全部留口**，本轮只有 clip + 交叉淡化 |
| 根运动（root motion） | **全文未提及** |
| 城市人群 | 500 实体上限 + LOD / impostor 留口 |
| 城市尺度 NPC 寻路 | 寻路在模块，navmesh 无归属 |
| 视野锥 / 警戒状态 | ✅ 射线查询 + 行为单元够用 |

**这不是缺陷，是取舍**：动画状态机 + IK + root motion 对单人项目是个无底洞，
而它对核心假设（I2 事件表可读、I3 同一种材料）零贡献。**但要写出来**——见下一节。

#### v17 的八款定案（本节现在是判据源 —— 决策 39）

**v17 起，A.9 不再是「压力测试」，它是范围纪律的判据源本身**（§3.2、§5.2）。
八款按簇排列，**判定用的是灰盒 MVP 标准**（核心玩法循环，几何体代替美术）：

| 簇 | 游戏 | 判定 | 关键依赖 |
|---|---|---|---|
| **俯视指令** | 红警 | ✅ | 群体寻路、视野迷雾、建造、数据表、lockstep |
| | 星际争霸 | ✅ 小规模 | 同上 + **1000 实体预算**（决 30 上调的直接原因） |
| | 魔兽争霸 | ✅ | 同上 + 英雄技能（技能目标选择 + 行为单元） |
| | Dota 2 | ✅ 单人对 AI | 技能目标选择（**核心**）、**物品栏（动态集合）**、视野 |
| **第三人称动作** | 塞尔达 | ✅ 神庙式 + 小区域 | **关节**（决 33）、动画状态机、背包、大世界流式 |
| | 艾尔登法环 | ✅ Boss 房 + 小区域 | **动画事件 + root motion**（决 36 的主要驱动者）、锁定、背包 |
| | 刺客信条 | ⚠️ **明确降级** | **潜入 + 战斗 + 沿预设点攀爬。没有丝滑跑酷**——那要动画档 3，已封顶（§3.4） |
| | **战争机器** | ✅ 单人 / 合作 | 动画档 2、射线命中、掩体。**不做竞技 FPS**（网络模型会裂成两套） |

**三条从这份清单读出来的结论**：

1. **八款里五款是联机游戏，且全部走 lockstep** → 决策 29 从「预付」变成「被证成」，网络模型不分裂
2. **没有一款需要网格世界、模拟分级、载具物理、样条路网** → v17 把这四项撤回为留口
3. **刺客信条是唯一一款要降级的** → 它的核心是移动手感，而那是动画档 3。**降级写死在决策 36，不再每轮回来一次**

#### 玩法契合度（v16 新增，风险 18 的应答）

**MVP 覆盖面与玩法的「节奏 + 相机」强相关**，因为整套架构的每一处选择都在往同一个方向使劲：

| 轴 | 玩法 | 为什么 |
|---|---|---|
| **强项** | RTS、MOBA、塔防、战棋、roguelite、经营 | 俯视 / 秒级 / 指令驱动。受限相机是默认（决 16）、确定性 + Action 日志天然是 lockstep 底座（A.9）、选择与指令在内核 |
| **中等** | 魂类 Boss 房、塞尔达神庙、平台跳跃 | 第三人称 / 房间尺度 / 帧级战斗。动画事件托住攻击判定，关节托住物理解谜；缺的是状态机 |
| **弱项** | 刺客信条类跑酷、character action | **移动本身即玩法**。整个动画栈封顶在 crossfade，这一类拿不下来 |

**这张表的用处是防止隐性判据**：闸门 F 只要求「一款能上架的完整作品」，
而「通用引擎」四个字会让人默认覆盖全部类型。**弱轴写出来，就不会在阶段三半路去补一个动画状态机。**

**v11 补的三个概念恰好托住了最硬的部分**——技能系统、buff、背包菜单、篝火存档、回合流程，
全部落在行为单元与流程上。**没有 v11 那轮，这五款一个都做不成。**

#### 补进内核的四项（v12）

| 能力 | 谁需要 | 归属 |
|---|---|---|
| 播放期**选择与指令** | Dota / 星际 / 红警 / 战棋 | 内核 |
| 播放期**放置与建造** | **塔防（本来就要）** / RTS / 城建 | 内核 |
| **动画事件**（clip 时间点） | 魂类 / 动作 / 任何有攻击判定的 | 内核 |
| **战争迷雾 / 视野** | 只有 RTS 类 | **模块** |

第四项**数值表达力**（伤害公式、成长曲线）列入未决项，触发条件是「实测写一遍公式」。

#### CS 为什么连 MVP 也拿不下

不是功能缺失，是三件结构上不做的事：**竞技网络**（服务器权威 + 客户端预测 + 延迟补偿，
与本项目的 lockstep 亲和性正好相反）、**手感精度**（亚帧命中、稳定高帧率，而预算是手机 30fps）、
**反作弊**。能做的只有「单人打 bot 的射击原型」，而 **CS 的体验核心是对枪**。

同样的道理对星际的天梯成立——但**星际的单人战役、Dota 的单人对 AI 都是完整体验，
只有 CS 的单人模式不构成一个游戏。**

#### 这次压测暴露的三条通用教训

| 发现 | 处理 |
|---|---|
| **拦住完整游戏的不是天花板，是三个架构缺口**（场景与流程、行为单元、运行期状态） | 全部补进 §4.7，数据模型阶段二定死 |
| **模板集选错会漏能力**——塔防与平台跳跃恰好都不需要那三样，所以架构漏掉了它们 | 加「完整作品模板」，决策 15 修订 |
| **确定性 + Action 日志 = lockstep 网络的天然底座** | 日后做联机**先做 RTS / MOBA 类**（指令同步），不要先做 FPS 类（服务器权威 + 客户端预测，代价大一个数量级）。回放是白送的 |

**还有一条 v12 才发现的**：现在的模板集（塔防 + 平台跳跃 + 完整作品）**仍然倒推不出
「选择与指令」和「动画事件」**——所以这两项是**按共性能力直接写进内核清单的，不是由模板倒推的**。
这是三次法则的一次例外，理由写在这里备查：**当五个主流玩法里有三个以上需要同一样东西时，
不必等模板出现。**

### A.11 决策 4（只做 3D）的依据（补于 v16）

**这一条一直没有依据条目，而它是全文成本最高的决策之一**——3D 把美术量、动画栈、
相机设计、性能预算全部乘上一个系数，**且对核心假设（I2 事件表可读、I3 同一种材料）零贡献**。
补写在这里，是为了让它和其他决策一样可被推翻。

**支持它的三条**：

| 依据 | 说明 |
|---|---|
| **差异化位置**（风险 10） | 2D 事件表引擎这一格**已经被 Construct / GDevelop 占满且做得很好**（A.1）。再做一个只能拼质量，拼不过十几年积累。「普通人能用的 **3D** AI 原生网页引擎」这一格才是空的 |
| **用户画像**（决策 19） | 会 Blender、理解变换与材质的人，**手里的资产和肌肉记忆都是 3D 的**。给他们 2D 反而要重学 |
| **决策 16 已应答了成本** | 「3D 是门槛」（风险 7）的答案是**受限 3D**：默认地面平面 + 固定相机档位。它把 3D 最劝退的部分（自由飞行相机）降级为一个档位 |

**要诚实记下的代价**：

- **视听下限（决策 23）在 3D 下贵得多**：一套 2D 的「像成品」只要美术风格统一；
  3D 的还要光照、材质、后处理、动画过渡各一套——**§3.4 视听表里六项本轮做，全部是 3D 带来的**
- **风险 11（内容生产量）大部分由这条决策产生**：素材库、皮肤包、模板关卡，3D 的工作量是 2D 的数倍
- **A.9 的弱轴也源于此**：2D 里「移动手感」是几张 sprite，3D 里是一整套动画状态机

**推翻它的条件**：若闸门 C 的真人实测显示，用户卡在**3D 空间操作**（摆放、对齐、相机）
而不是卡在事件表，则决策 16 的受限 3D 已经不够，**此时该重估决策 4，而不是继续给 3D 加辅助工具**。

> **v17 补充**：这一条的第二、三行依据（用户画像、决策 16 的受限 3D）**随画像一起失效了**。
> 但结论**更稳**——目标用户本来就在 3D 里工作，八款目标游戏全是 3D。
> **真正剩下的代价只有一条**：§3.1 的三款参照（星露谷 / 空洞骑士 / 吸血鬼幸存者）全是 2D，
> **「一个人能做完」这个水位在 3D 下没有被参照过**。这条挂在这里，等闸门 F 给答案。

### A.12 决策 35：为什么门槛可以交给 AI 与教程

原文档用画像反推了四条约束——**双模式、术语层、削表达力、概念数量上限**。
它们的共同前提是「用户是不写代码的普通人」，而那是全文**最容易变、也确实变了**的一条假设。

**v17 的做法不是把门槛取消，是换一个承担者。** 三条理由：

| 依据 | 说明 |
|---|---|
| **架构已经把 AI 的门槛压得很低**（[A.7](#a7-决策-21为什么接各种模型是可行的)） | 三个入口、渐进披露、Action 序列而非整图、约束层给结构化反馈、优先挑配方填参——**这些设计本来就是为了让弱模型也能干活**。让 AI 承担「我不知道怎么做」，是这套架构的自然推论，不是新负担 |
| **教程比裁剪界面便宜，而且不损失能力** | 裁剪界面要维护两套暴露面、两套默认值、一套术语映射，且**永久钉死了简易侧的上限**（M3）。教程是内容，**加了不影响能力，删了不影响架构** |
| **教程能跟着能力一起交付** | §1.4 的新原则「每个概念自带入口」把它变成可判定的：**加一个概念就要交一条教程**。这比「概念总数有上限」更可执行，也不需要知道用户是谁 |

**代价必须写明**：

- **AI 从卖点变成承重结构**（风险 4 加重）。AI 挂了，门槛就没人承担——所以「失败兜底」这条非功能项从此与功能同级，教程与配方必须能独立扛住
- **教程是内容生产**，会撞上风险 11。**但它比模板与皮肤便宜得多**，且不做的后果更贵
- **这条决策有一个可判定的失败信号**：闸门 D.5「教程可用性」。连续两轮不过 → 走项目级退役条件 **P-2**，回头重估决策 12 的取消

**一句话**：**画像会变，AI 与教程这两个承担者不会因为画像变而失效。**
这正是「不要被画像限制」的可操作含义——**不是无视用户，是不把用户画像刻进架构。**

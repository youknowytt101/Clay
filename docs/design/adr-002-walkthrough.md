## 0. 结论先说

> **三个样例都不能按现有 §3–§7 直接走通。** 共暴露 **6 处语义缺口**，其中
> **A、B、D 是阻塞级**——不补就无法判定样例是否"走通"，因而闸门 O 无法通过。

**最重要的发现是 D：同一物理步内产生的多个触发事件，入队顺序未定义。**
它不是语义歧义，是**确定性漏洞**——两台机器同一输入可以跑出不同结果，直接威胁决策 29 与 lockstep。
ADR-002 §8 的 D1 只规定了**实体迭代顺序**，漏了**事件顺序**这另一半。

D 同时改变了 Rapier spike 的验收内容：只验刚体状态逐帧哈希一致**不够**，必须同时验接触事件序列一致。

## 1. 方法

对每个样例，按 [ADR-002 §3](adr-002-eventsheet-eval.md) 的 tick 流程逐步推演，
在每一步记录**各种类的当前集合**。凡是"按规则推不出唯一结果"的地方即记为缺口。

判据来自 ADR-002 §9 原文：**结果与「用户读这段规则会预期什么」一致；任一条不一致 → 改语义，不改样例。**

## 2. 样例一 · 塔防选目标

```
当  敌人 进入 塔的范围          ← 触发型
    塔 冷却完毕
就  塔 朝 距离最近的 敌人 开火
    塔 进入冷却
```

世界：塔 `T1(0,0)`、`T2(10,0)`，射程 5；敌人 `E1`、`E2`、`E3`。

### 2.1 推演：单个事件 → 撞上缺口 A

tick N，`E1` 移入 `T1` 范围（距离 3）。step 2 物理步进产生进入事件，载荷 `(敌人=E1, 塔=T1)`，入队。
step 3 排空，执行该规则分支。**此时初始集合是什么？**

| 依据 | 说法 | 推出的集合 |
|---|---|---|
| §4 | "每条顶层规则从**全集**开始" | 敌人 `{E1,E2,E3}`、塔 `{T1,T2}` |
| §3 | "按入队顺序 FIFO，**逐个**执行其规则分支" | 暗示载荷参与定集，否则"逐个"没有意义 |

**两节各自读都成立，合起来推演就撞车。** 若真从全集开始，任意一对进入范围会让**所有**冷却完毕的塔开火。

> **缺口 A · 触发规则的初始集合未定义。**

**候选**

- **A1（推荐）**：触发规则的初始集合 = **触发载荷涉及的实体**，每个被载荷提及的种类为单元素集；
  **未被载荷提及的种类仍从全集开始**。
- **A2**：从全集开始，触发条件充当筛选器，选出本 tick 内发生该事件的全部实体，**一次**执行。

**取 A1 的理由**：A2 会让 §3 的 FIFO"逐个"与排空深度上限 N 同时失去意义；
且 ADR-002 §3 自称"不另发明，沿用 Construct / GDevelop 被验证的模型"，而这两家的触发条件正是 picks 触发它的实例。

### 2.2 推演：两个敌人同 tick 进入 → 撞上缺口 B

设 `E1`（距 T1 = 3）与 `E2`（距 T1 = 1）**同 tick** 进入 `T1` 范围。两个事件入队。

按 A1 逐个执行：

| 步 | 事件 | 敌人集 | 塔集 | 结果 |
|---|---|---|---|---|
| 1 | `(E1,T1)` | `{E1}` | `{T1}` 冷却完毕 ✓ | T1 打 **E1**，T1 进入冷却 |
| 2 | `(E2,T1)` | `{E2}` | `{T1}` 冷却中 ✗ → **空集** | 整条不执行（Q3） |

**结果：T1 打了 E1，而 E2 更近。** 与样例自己写的验证目标"两座塔各打各的**最近**目标"不符。

根因：在 A1 下敌人集是**单元素**，动作参数 `距离最近的 敌人` 退化成恒等——它没有可选择的余地。
要真正选到最近的，该参数必须解析为"**当前这座塔**射程内的**全部**敌人中最近的一个"，这需要两样 §4 没有的东西：

1. 相对于当前动作执行实例（塔）的**关联作用域**；
2. **突破当前集合**去查询更大范围的能力——而 §4 的模型是**只收窄不放宽**（单调收窄）。

> **缺口 B · 选择器式动作参数（"距离最近的 X"）的作用域未定义，且与 §4 的单调收窄模型冲突。**

**候选**

| | 方案 | 评价 |
|---|---|---|
| B1 | 改写样例为常规规则（每帧：塔冷却完毕 + 范围内有敌人 → 打最近） | **不解决根本**："范围内有敌人"仍需关联作用域 |
| B2 | 引入通用关联作用域（**改 §4**）：动作逐个执行时为当前实例建作用域，其他种类在该作用域内重新求值 | 表达力最强，但破坏 P2/P3 的简单心智模型，且**必须在冻结前改主体语义** |
| **B3（推荐）** | 把"最近的 X"做成**显式的关联收窄条件**而非动作参数：`塔 的射程内 距离最近的 敌人`，注册为一类同时收窄两个种类并建立配对的条件 | 语义**局部化**，§4 主体不动；符合 §10"加受限原语，不改求值语义"的精神 |

**B3 的窗口现在开着**：§10 写的退役条件是"阶段二发现写不出来 → 加受限原语"。
但这次是**冻结前**发现的，所以还可以选择改语义（B2）；一旦冻结，就只剩加原语（B3）一条路。
**这是本次推演唯一真正需要你拍板的方向问题。**

### 2.3 推演：击杀后的第二个事件 → 撞上缺口 C

设 `E1` 同 tick 进入 `T1` 与 `T2` 的范围（两个事件），且一发即杀。

- 执行 `(E1,T1)`：T1 打 E1 → **E1 销毁**（Q4：动作立即写世界）。
- 执行 `(E1,T2)`：载荷敌人 `E1` **已不存在**。语义未定：跳过？还是对已销毁实体开火？

§7 的 **W3** 给了对称先例（等待队列快照里的实体已销毁 → 跳过，不报错、不整条中止），
但它只覆盖**等待队列**，没有覆盖**触发队列的载荷**。

> **缺口 C · 排空期间触发载荷实体被销毁时的语义未定。**

**候选（推荐）**：补一条 **E4**——排空时若载荷实体已销毁，**跳过该事件**，不报错、不中止后续事件。与 W3 对齐。

### 2.4 推演：换一台机器 → 撞上缺口 D（最严重）

回到 2.2：结果取决于 `(E1,T1)` 与 `(E2,T1)` **谁先入队**。

§3 只说"按**入队**顺序 FIFO"，**没有规定同一物理步内产生的多个事件按什么顺序入队**。
§8 的 **D1** 规定了实体迭代按稳定 id 升序，但那管的是**全表求值时的实体遍历**，不管**物理引擎回调的事件顺序**。

而 Rapier 的接触事件顺序来自它内部的宽相 / 窄相遍历，**不保证跨平台、跨版本一致**。

> **缺口 D · 同一 step 内产生的触发事件，入队顺序未定义 → 直接击穿决策 29。**
>
> 后果链：事件顺序不同 → 2.2 的"T1 打 E1 还是 E2"不同 → 世界状态分叉 → lockstep 立即失步。
> 这不是"可能有性能差异"级别的问题，是**同一份作品在两台机器上跑出不同结果**。

**候选（推荐）**：补 **D4**——同一 step 内产生的触发事件，入队前按
`(事件类型 id, 主实体 id, 次实体 id)` **稳定排序**。这是 D1 在事件层的对应物；
§8 只做了实体迭代那一半，事件那一半一直缺着。

**对 Rapier spike 的影响**：M1-e 的验收必须从"逐 tick 刚体状态哈希一致"扩展为
"**逐 tick 刚体状态哈希一致 + 逐 tick 接触事件序列一致**"。若 Rapier 的事件顺序本身不稳定，
D4 的排序层就是必需的（而不是可选的加固）——这一点 spike 可以直接测出来。

## 3. 样例二 · 跳跃缓冲

```
当  意图「跳跃」被按下              ← 触发型
就  设置 变量 缓冲 = 0.15 秒

每帧
    缓冲 > 0
    角色 在地面上
就  角色 向上施加冲量
    设置 缓冲 = 0
```

### 3.1 通过的部分

tick N（角色在空中，玩家按跳跃）→ tick N+2（落地）：

| 步 | 发生什么 |
|---|---|
| N.1 | 采样输入，冻结快照 |
| N.3 | 排空触发：`缓冲 = 0.15` |
| N.4 | 全表：`缓冲 > 0` ✓，`在地面上` ✗ → 不执行 |
| N+2.4 | 全表：`缓冲 > 0` ✓，`在地面上` ✓ → 施加冲量，`缓冲 = 0` |

- **E1 验证通过**：触发（step 3）先于全表（step 4），所以"落地前按的跳跃仍然生效"成立 ✓
- **Q4 验证通过**：同一条规则内先施加冲量后置零，后续规则读到 `缓冲 = 0` ✓

### 3.2 缺口 E · 计时器与 `dt`

样例写 `缓冲 = 0.15 秒`，带时间单位，**暗示它会自动随时间递减**。
但 §3 的 tick 流程里**没有"变量按秒递减"这一步**，§7 的等待队列只处理 `等待` 动作的续延。

若要求用户自己写 `每帧 → 缓冲 = 缓冲 - dt`，则：样例二**少了一条规则**，且 `dt` 从哪来也没定义——
§8 的 D3 注入了 `rng` 与 `tick`，**没有 `dt`**。

> **缺口 E · 带时间单位的变量（计时器）是不是一等概念？`dt` 是否注入？**

**候选（推荐）**：计时器作为**一等概念**——声明为计时器的变量由内核在 step 5（等待队列结算）统一递减，
与等待队列同属运行期状态、同样可序列化（W2 的理由完全适用：技能冷却、波次间隔、跳跃缓冲都是计时器）。
理由：若交给用户手写递减，每个作品都会重新实现一遍，且**忘记存档**的概率极高，直接撞 I11。

### 3.3 A1 的子情形：无实体载荷的触发

`意图「跳跃」被按下` 是触发型，但**不携带实体载荷**。按 A1"未被载荷提及的种类从全集开始"，
角色集 = 全集。单角色无碍，**多角色（分屏 / 联机）就会让所有角色一起跳**。

→ A1 需补充一句：**输入意图类触发不携带实体载荷**，要绑定到具体角色须写显式条件（如 `角色 是本地玩家`）。
这不是新缺口，是 A1 措辞的必要补全。

## 4. 样例三 · RTS 下达指令

```
当  意图「确认」被按下              ← 触发型
    存在 被选中的单位
就  被选中的单位 移动到 光标位置

当  单位 到达目标点
就  单位 播放「待机」
    等待 0.3 秒                     ← W2 快照
    单位 朝向 默认方向
```

### 4.1 通过的部分

- **P3 验证通过**：规则 2 从全集重新开始，不受规则 1 的选中集影响 ✓
- **W2 / W3 验证通过**：`单位 到达目标点` 是触发型，按 A1 载荷 = 到达的那个单位，
  每个单位各自触发、各自等待；等待期间该单位被摧毁 → W3 跳过 ✓
  （在 A1 下这条比样例设想的"一批单位一起等待"语义**更干净**）

### 4.2 缺口 F · 「存在 X」是布尔还是筛选

`存在 被选中的单位` 落在 §5 没有覆盖的中间形态：

| §5 覆盖的 | 本例 |
|---|---|
| 取反条件（"没有敌人在范围内"）→ 只做布尔判定，不改集合 | ？ |
| 纯布尔条件（"金钱 > 100"）→ 不改集合 | ？ |

- 若判为**纯布尔不收窄** → 单位集仍是全集 → 动作 `被选中的单位 移动到 光标位置` 对**全集**执行 → **所有单位都移动**。错。
- 若判为**筛选** → 它就是普通条件，"存在"两字只是措辞。

> **缺口 F · 「存在 X」形式的条件是布尔判定还是筛选条件？**

**候选（推荐）**：**不设独立的"存在"形态**——`存在 被选中的单位` 就是筛选条件 `单位.被选中 == true`，
其"存在"语义由 **Q3 的空集规则自动获得**（筛出空集 → 整条不执行）。
但这必须**写明**，否则实现者会照字面做成布尔条件，而这个错误在单元测试里不容易暴露
（单选一个单位时两种语义结果相同，多选时才分叉）。

## 8. 第二轮推演（对 r2 语义）

项目所有者裁决：缺口 B 取 **B3′ 参数化关联原语族**。ADR-002 据此出 **r2**。本节按 r2 重推三个样例。

### 8.1 样例一 · 关联查询（缺口 B）

```
每帧
    塔 冷却完毕
    塔 的 射程内 最近 的 敌人
就  塔 朝 配对的 敌人 开火
    塔 进入冷却
```

世界：`T1(0,0)`、`T2(10,0)` 射程 5；`E1`(距 T1 = 3)、`E2`(距 T1 = 1)、`E3`(距 T2 = 2)。

| 步 | 集合状态 |
|---|---|
| 顶层起点 | 塔 `{T1,T2}`、敌人 `{E1,E2,E3}` |
| `塔 冷却完毕` | 塔 `{T1,T2}`；**敌人不受影响**（P1） |
| 关联查询 | T1 射程内 `{E1,E2}` → 最近 `E2`；T2 射程内 `{E3}` → 最近 `E3`<br>配对 `(T1,E2)`、`(T2,E3)`；塔 `{T1,T2}`、敌人 `{E2,E3}` |
| 动作 | 按配对：T1 打 **E2**，T2 打 **E3** |

> **两座塔各打各的最近目标 ✓ 缺口 B 闭合。**
> 全部敌人在射程外时无配对 → 塔集为空 → 整条不执行 ✓（Q3）

### 8.2 但第二轮撞出新缺口 G

接上例，改设 `E2` 同时在 T1 与 T2 的射程内且对两者都最近 → 配对 `(T1,E2)`、`(T2,E2)`。
按 D1 稳定 id 升序，T1 先执行。设一发即杀：

- T1 打 `E2` → **`E2` 销毁**（Q4：动作立即写世界）
- 轮到 `(T2,E2)` —— **配对的另一端已经不存在了。** 语义未定。

> **缺口 G · 关联查询的配对在动作阶段失效时的语义未定。**

**这是同一个模式第三次出现**：

| 出处 | 被快照的东西 | 语义 |
|---|---|---|
| **W3**（r1 已有） | 等待队列里的实体集 | 跳过该实体 |
| **E4**（r2 新增） | 触发队列里的载荷 | 跳过该事件 |
| **G → R4**（本轮新增） | 关联查询的配对 | ？ |

前两处已经定成"跳过、不报错、不中止其余"，第三处没有理由不同。
**已定为 [R4](adr-002-eventsheet-eval.md#41-关联查询原语族r2-新增--b3)：跳过。**

**为什么不选"重新查询次优目标"**——这是决定性的一条：

> 重查意味着**动作阶段还要再做一次查询**，等于承认目标不是条件阶段定好的，而是边执行边算的。
> **那正是 B2 通用作用域的做法**，而我们刚刚因为它不可逆、语义未推演而放弃了它。
>
> 从这个小口子放它进来，等于**在没人注意的地方绕过了 B3′ 这个决定**。
> R4 选"跳过"不只是更简单，是**保持已作出的决定不被悄悄推翻**。

另两条支持理由：三处同构一套规则比三种特例好实现好测；少打一帧是 1/60 秒，
且用户想要次优目标行为时自己加一条规则即可——引擎不该替他决定。

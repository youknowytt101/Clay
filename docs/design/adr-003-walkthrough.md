## 0. 结论先说

> **8 处缺口，其中 2 处阻塞、2 处关键。**

**最重要的两处**：

- **缺口 C · `baseRevision` 在多步骤中怎么推进没有定义** —— 按字面实现，**任何多步计划的第二步都会永远冲突**。
- **缺口 E · 鼠标点击这条路径没有 hard oracle** —— 而 S2 的整个存在意义就是防止这类"错误通过"，
  §9 还要求错误通过率必须为 0。

这两处都落在 **M1-b（Action 事务字段）冻结前**必须解决的范围内。

## 1. S1 · 加一种会飞的敌人

计划：新增 kind → 配皮肤 → 移动行为 → 生成规则行 → 加入关卡 → 验证。
人工制造一次皮肤缺失约束。

### 1.1 缺口 A · 「验证」不该是一个 PlanStep（轻）

§10 把"验证"列为计划的一环，但 §3.1 里每个 `PlanStep` 自带 `acceptance`，
`PlanContract` 另有 `globalAcceptance`。**验证是每步的属性，不是步骤。**

若真把它做成步骤，会立刻产生递归问题：**这个验证步骤自己的 `acceptance` 是什么？**

**候选（推荐）**：措辞澄清——计划里不出现"验证"步骤；端到端验收放 `globalAcceptance`。无需改结构。

### 1.2 缺口 B · 步骤 checkpoint 可能是**约束违反**的状态（阻塞）

推演 s1（新增 kind `flying_enemy`）→ s2（配皮肤映射，人工制造缺失）：

| 步 | 事务 | 结果 |
|---|---|---|
| s1 | preview → V1 通过（kind 结构合法）→ **commit → checkpoint1** | 工程里有了 kind |
| s2 | preview → V1 **失败**（约束层：kind 缺少皮肤映射）→ 丢弃候选分支 | 回到 checkpoint1 |

**此时 checkpoint1 是一个约束违反的状态**：有 kind，没皮肤。

而 §10 要求"检查逐步 checkpoint、**部分接受**与证据完整性"。
**部分接受一个约束违反的状态，是什么语义？** 用户按下"接受已完成的部分"，
拿到的是一个约束层会持续报错的工程。

根子在于：**步骤级 `acceptance` 与全局约束的关系没有定义。**

- 若要求每步都满足全局约束 → **无法增量构建**（kind 与皮肤必须原子地一起做完，计划就没法拆细）
- 若只在 `globalAcceptance` 查全局约束 → 中间 checkpoint 可以是坏的，**"部分接受"变成一个危险操作**

**候选**

| | 方案 | 评价 |
|---|---|---|
| B1 | 约束分级：**阻断性**（引用完整性、schema）与**完成性**（kind 缺皮肤）。只有前者阻止 commit | 与"增量构建"相容；需要给约束层加一个等级字段 |
| B2 | 引入**步骤组**，组内共享一个 checkpoint，组外才可部分接受 | 表达力强，但 `PlanContract` 要加一层结构 |
| **B1 + C3（推荐）** | B1 分级，**且部分接受时必须显示"当前有 N 条完成性约束未满足"** | 用户仍可部分接受，但**知道自己接受的是什么**。契合 [I2](goals.md#02-十二条不变量) 的可审计 |

### 1.3 缺口 C · `baseRevision` 在多步骤中怎么推进（**阻塞**）

§3.1 的 `PlanContract` 有**一个**计划级 `baseRevision`；
§5.1 说"校验 `baseRevision`，不一致则停止并报告冲突"；
§3.3 的 `StepReceipt` 却有**每步自己的** `beforeRevision` 与 `candidateRevision`。

**三者关系未定义。** 按 §5.1 的字面实现：

- s1 执行前校验：工程 revision = `R0` = `PlanContract.baseRevision` ✓ → commit → 工程变成 `R1`
- s2 执行前校验：工程 revision = `R1` ≠ `PlanContract.baseRevision`（`R0`）→ **停止，报告冲突**

> **任何多步计划都会在第二步永远冲突。**

**候选（推荐）**：两个字段职责分开写明——

| 字段 | 语义 | 何时校验 |
|---|---|---|
| `PlanContract.baseRevision` | 计划**创建/批准时**的工程 revision | **仅在第一个步骤执行前**校验；用于检测"批准后、执行前工程被改过" |
| `StepReceipt.beforeRevision` | 本步骤执行前的 revision（= 上一步的 `candidateRevision`，或首步的 `baseRevision`） | 每步校验，用于检测**本 run 之外**的并发修改 |

关键是把"冲突"重新定义为：**revision 变化不是由本 run 的已提交步骤造成的**。
本 run 自己推进 revision 不算冲突。

### 1.4 缺口 D · 修复能用哪些 Action 没有定义（中）

§4 的状态机里 `Repairing → Executing`，**不回到 `AwaitingApproval`**。
§3.1 又说"计划的每次修改都增加 `version`，未执行步骤回到待批准状态"。

于是：**修复算不算"计划修改"？**

- 算 → 每次修复都要人重新批准 → **自主循环不成立**
- 不算 → 修复引入的 Action **绕过了"批准绑定 version"这道门**

而 §7 的停止条件里有"需要现有 registry 没有的新条件或动作"，
**却没有"需要本步骤 `allowedActions` 之外的 Action"**。

S1 正好能触发它：如果皮肤缺失是因为 s1 里 kind 名字拼错了，
**最小修复是回去 rename kind——那是 s1 的影响域，不是 s2 的**。

**候选（推荐）**：修复**只能使用本步骤已批准的 `allowedActions`，且不得改动任何 `acceptance`**；
需要触碰其他步骤的影响域时，走 `NeedsReview` 回到审批。在 §7 的停止条件里补这一条。

## 2. S2 · 按钮能看到但点了没反应

### 2.1 缺口 E · 鼠标点击这条路径**没有 hard oracle**（**关键**）

§10 写：**"V2 用输入意图驱动菜单，V3 用真实鼠标点击。直接调用按钮回调或传送到结果状态不得算通过。"**

按现有定义推：

| 层 | 驱动方式 | severity |
|---|---|---|
| **V2** | `inputTrace: InputIntent[]`——而 [I12](goals.md#02-十二条不变量) 规定意图是 `跳跃 / 确认 / 移动`，**不含坐标** | 可以 `hard` |
| **V3** | 真实鼠标点击 | §3.2：`visual` **默认只能是 `soft`** |

于是"确认"意图只能驱动**焦点模型**（键盘式导航：下一项 / 确认），
而**鼠标命中测试那条路径，V2 到不了、V3 判不了硬**。

> **结果：按钮的鼠标绑定断了，V2 仍然全绿。**
> 而这正是 S2 想要防的那种错误通过，也直接违反 §9 的"错误通过率必须为 0"。

**根因是把"设备无关"用错了地方。** [I12](goals.md#02-十二条不变量) 管的是
**事件表不得引用设备**——那是被测对象的约束；**测试轨迹不是事件表**，
它完全可以在设备层驱动，只要被测逻辑本身只认意图。

**候选（推荐）**：`inputTrace` **分两层**——

```ts
type InputTrace =
  | { layer: 'intent'; intents: InputIntent[] }      // 驱动玩法逻辑
  | { layer: 'device'; events: DeviceEvent[] };      // 驱动输入映射与 UI 命中测试
```

并明确：**`kind: 'interaction'` 的 device 层测试可以是 `hard`**。
理由是它的判据是**可判定的**（按钮是否被激活、菜单是否关闭），不是视觉判断——
`visual` 默认 soft 那条规则针对的是"截图好不好看"，不该殃及命中测试。

### 2.2 缺口 F · 回归测试范围由谁决定（**关键**）

§7 要求修复产出"受影响测试与**必须重跑的回归测试**"，§10 要求"重跑原测试与**菜单回归测试**"。

**"菜单回归测试"这个集合是谁圈定的？**

- 由 **AI** 判断哪些相关 → 它可以**选择性少跑**。这**绕过了** §7"试图删除、放宽或跳过 hard TestSpec"
  那条停止条件——因为它既没删也没放宽，只是**没跑**
- 由**引擎**按影响域推导 → 需要 TestSpec ↔ 实体 / 系统的依赖索引，**ADR 里没有这个结构**

> 这是"错误通过"的一条**隐蔽路径**：所有跑过的测试都是绿的，只是该跑的没跑。

**候选（推荐）**：`TestSpec` 增加 `covers: string[]`（它断言了哪些实体 / 系统 / 规则组）；
回归范围由**引擎**按本步骤实际 `affects` ∩ 各 TestSpec 的 `covers` 求出，**AI 只能建议扩大，不能缩小**。

## 3. S3 · 请求 registry 不具备的新原语

### 3.1 缺口 G · Action 存在性检查发生在什么时候（轻）

§4 里 `Draft → AwaitingApproval` 的条件是"计划结构合法"。
**这是否包含"`allowedActions` 里的 id 都在 registry 中存在"？** 未说明。

**候选（推荐）**：包含。计划校验期就查 id 存在性——**尽早失败**，
不要让一个引用了不存在 Action 的计划走到人工审批。

但要注意这**不是 S3 说的那件事**（见下）。

### 3.2 缺口 H · 能力缺口没有独立的识别机制（中）

S3 要的不是"引用了不存在的 action id"，是"**这个需求没法用现有原语表达**"——
比如"逃跑时留下燃烧的痕迹"，registry 里没有任何动作对应"留下持续痕迹"。

**这个判断只有模型能做，引擎无法自动检测。** 而模型最常见的失败模式恰恰是
**硬凑一个近似实现**（用现有原语拼个不对的东西），而不是承认做不到。

现有机制的兜底路径是：硬凑 → `acceptance` 不符 → 修复 → 同一失败签名两次 → 停止。
**机制上确实会停**，但停下来时报告的是"**重复失败**"，
而 §10 要求 S3 的输出是"**指出缺少的条件 / 动作**"——用户拿不到那个诊断。

**候选（推荐）**：在 `PlanStep` 增加一个计划期必填字段
`primitivesUsed: string[]`（本步骤打算用哪些条件 / 动作达成 `intent`），
并要求 planner 在无法用现有原语表达时**显式产出 `capabilityGap`** 而不是留空。
`capabilityGap` 非空 → 计划直接停在 `NeedsReview`，不进入执行。

这把"承认做不到"从**模型的自觉**变成**计划结构的必填项**——
模型可以填错，但**填不出来这件事本身会暴露**。

**E 与 F 是同一类问题的两面**：验证看起来通过了，但**该验的路径没被验**。
§9 把"错误通过率必须为 0"定为硬线，而这两处正是它现在最可能被击穿的地方。

## 5. 闸门判定

> **ADR-003 的三个手工样例：未通过。**
>
> S1 在第二步撞上 B 与 C（C 会让任何多步计划无法执行）；
> S2 的核心诉求（防止用 shortcut 冒充 UI 验证）在现有 `TestSpec` 定义下**做不到**；
> S3 能停下来，但给不出它自己要求的诊断。
>
> **协议的骨架是对的**——状态机、事务边界、权限隔离、有界修复都站得住，
> 缺的是**字段级的语义**。这与 ADR-002 第一轮的情况同构：大结构没问题，
> 真推演撞出来的全是"两节各自读都成立、合起来推不出唯一结果"的接缝。

**C、D 必须在 M1-b（Action 事务字段）冻结前定**；E、F 可以到 M3-f，
但**越晚定，已经写好的 TestSpec 越多，改起来越贵**。

## 7. 第二轮推演（对 r2 协议）

### 7.1 S1 重推

| 步 | r2 下的行为 |
|---|---|
| s1 新增 kind | revision `R0` = 计划 `baseRevision` ✓（首步才查）→ V1：阻断性约束通过，**完成性约束「缺皮肤」记入 receipt 不阻止 commit**（6.1）→ checkpoint1，工程 `R1` |
| s2 配皮肤（人工制造缺失） | `beforeRevision` = `R1` = s1 的 `candidateRevision` ✓ **不再误判为冲突**（3.1.1）→ 约束失败 → Repairing |
| 修复 | 补映射在 s2 的 `allowedActions` 内 → 环内修复，无需人介入 ✓ |
| 若缺失源于 s1 拼错 kind 名 | rename 超出 s2 影响域 → **`NeedsReview`**（§7 新增停止条件）✓ |
| 部分接受 | 显示「1 条完成性约束未满足：kind `flying_enemy` 缺皮肤映射」✓ |

> **B、C、D 闭合。** C 尤其关键——r1 下这个计划**根本走不到 s2**。

### 7.2 S2 重推

- V2：`{ layer: 'intent' }` 驱动焦点模型 → 验键盘/手柄路径
- V3：`{ layer: 'device' }` 真实鼠标事件 → `kind: 'interaction'`、`severity: 'hard'`（r2 放开）
- 植入断开的鼠标绑定 → **device 层 hard 失败** ✓ **v1 下这里是全绿的**
- 修复后回归范围 = `{ t | t.covers ∩ affects ≠ ∅ }` 由引擎求出 → 菜单回归自动纳入，**AI 无法少跑** ✓

> **E、F 闭合。** 这两处是 §9「错误通过率 0」能否成立的前提。

### 7.3 S3 重推

- planner 读 registry，"留下燃烧的痕迹"无对应原语
- `primitivesUsed` 是**必填**，填不出来 → 必须产出 `capabilityGap`
- `capabilityGap` 非空 → **计划停在 `NeedsReview`，不进入执行** ✓
- 报告含：缺哪些能力、尝试过什么、为何不足、已完成步骤、未执行步骤、最后 checkpoint ✓

> **G、H 闭合。** r1 下的兜底路径是"硬凑 → 两次失败 → 停止"，
> 报告写的是"重复失败"而非"缺少原语"；r2 让它**在计划期就暴露**。

### 7.4 第二轮判定

> **三个样例全部走通，八处缺口全部闭合。**
>
> 但 **ADR-003 仍不能转「已验证」**——它自己 §10 的转状态条件是
> **两条**：三个样例纸面无歧义（✓ 已达成）**且**
> 「最小纵切中，事务回滚、计划版本失效、重复请求幂等、错误通过负例全部通过」（✗ 需要 M1-b 的实现）。
>
> **纸面部分完成，实现验证待 M1-b。**

## 1. 复现

```bash
npm install
npm run spike:gate-a -- --emit gate-a-x64.json
```

场景：地面 + 50 个盒子（5×5×2 网格，两层错位堆叠），固定步长 1/60，跑 600 步。
刻意制造堆叠与大量接触，放大非确定性。

采集两条序列，**逐 tick** 各取一个哈希：

| 序列 | 内容 | 为什么要它 |
|---|---|---|
| **状态** | 全部刚体的 `translation` + `rotation`，**精确位模式，不量化** | 量化会掩盖真实的跨平台漂移 |
| **事件** | `drainCollisionEvents` 交回的接触事件，**按原始顺序，不排序** | [ADR-002 推演缺口 D](adr-002-walkthrough.md#24-推演换一台机器--撞上缺口-d最严重) 新增的验收内容 |
| **Transform** | 四层非均匀缩放 / 旋转层级的 world position / quaternion / scale，**精确 f64 位模式** | `U-046`：验证 three.js `decompose()` 的结果是否跨 CPU 架构一致 |

> **事件序列这一半是这次新加的。** 原验收只写"逐帧状态一致"，
> 而 ADR-002 的推演表明：**事件顺序不一致同样会让作品分叉**，且它不体现在刚体状态里。

```
接触事件总数：156 / 156

事件序列一致：是

跨机器比对指纹：
  state = 85cff7f8f866e20f
  event = 3f0480a84fcddd29
  transform = d7f8d8b3699f8168
```

### 2.1 指纹有效性（植入负例）

**"通过"必须先证明测法能检出差异**，否则可能只是哈希没在测东西。
给首个盒子的初始 x 加不同量级的扰动：

| 扰动 | 状态 | 事件 |
|---|---|---|
| `1e-12` | 一致 | 一致 |
| `1e-9` | 一致 | 一致 |
| `1e-7` | 一致 | 一致 |
| **`1e-6`** | **分叉**（step 0） | 一致 |
| `1e-5` | 分叉（step 0） | 一致 |
| `1e-3` | 分叉（step 0） | 一致 |

**第一轮我用的是 `1e-12`，没被检出，一度以为指纹失效。** 实际原因是——

> **Rapier 内部是 f32（单精度）。** 在 `x ≈ -2.1` 附近，f32 的 epsilon 约 `2.4e-7`，
> 小于它的扰动在写入时就被吞掉了，世界根本没有变化。

检出阈值落在 `1e-7` 与 `1e-6` 之间，与 f32 精度边界吻合。**指纹有效。**

### 2.2 第二个数据点：浏览器 wasm 运行时

同一场景在浏览器里重跑（`browser.html`，脚本逻辑与 node 版逐行对应）：

```
UA: Chrome/148.0.7778.280 Electron/42.7.0 (Win64 x64)

接触事件总数：156 / 156
状态序列一致：是
事件序列一致：是

  state = 85cff7f8f866e20f      ← 与 node 完全一致
  event = 3f0480a84fcddd29      ← 与 node 完全一致
```

**两个指纹与 node v24.16 逐位相同。**

**这个数据点的价值有限，必须说清楚**：node 与 Chromium **都是 V8**，
只是版本不同（node 24 与 Chrome 148 的 V8 相差若干个大版本）。
所以它证明的是"**同一 CPU 上，不同 V8 版本的 wasm 编译对本负载产生相同结果**"，
**不是**"不同 wasm 运行时一致"——那需要 SpiderMonkey（Firefox）或 JavaScriptCore（Safari）。

它排掉的风险类别是真实的（引擎升级导致作品行为漂移），但**离跨 CPU 架构还很远**。

### 2.3 意外发现：**跨 Rapier 版本不一致**（严重）

M0-b 建工程时 `package.json` 写了 `^0.19.0`，装到 0.19.3；而本 spike 首轮在无约束环境下装的是 0.20.0。
同一脚本、同一场景、同一台机器，两版跑出来：

| Rapier | state 指纹 | event 指纹 | 接触事件总数 |
|---|---|---|---|
| **0.20.0** | `85cff7f8f866e20f` | `3f0480a84fcddd29` | **156** |
| **0.19.3** | `423ad71a6a8944ef` | `cde8f9ff8cf61410` | **693** |

**事件总数差 4.4 倍——这不是浮点噪声，是行为变更**（很可能是接触事件的生成或去重语义改过）。
**根因未查**：无论是 API 语义变更还是回归，结论都一样。

> **这直接撞不变量 I11**（已发布的作品必须永远能打开，且**跑出来的行为不变**）。
>
> **它比跨平台差异更紧迫**：跨 CPU 架构的差异**可能**存在；
> 而依赖升级是**必然发生**的——一次 `npm update` 就够了。

**已采取的措施**：`package.json` 的物理与渲染依赖全部改为**精确版本**（不用 `^` 范围），
并在文件里写明理由。**但锁版本只解决"我们自己不漂"，不解决"将来必须升级时老作品怎么办"**——
后者需要在快照里记录物理引擎版本，属于 I11 迁移链的一部分，已登记为 [`U-039`](goals.md#九--未决项)。

## 3. 这一轮证明了什么、没证明什么

| | |
|---|---|
| **已证明** | 同一进程内两个独立 world，同一输入 → 状态与事件序列**逐 tick 完全一致**；采集方法对 ≥ f32 精度的差异敏感 |
| **已证明** | 同一 CPU 上，**node 与浏览器（两个不同版本的 V8）结果逐位相同** |
| **未证明** | **跨机器、跨 OS、跨 CPU 架构（尤其 x64 ↔ ARM）是否一致** —— 这才是决策 29 与 lockstep 真正需要的 |
| **已证伪** | **跨 Rapier 版本不一致**——0.19.3 与 0.20.0 行为不同（见上文第 2.3 节）。版本必须锁死并进快照 |
| **未证明** | 非 V8 的 wasm 运行时（SpiderMonkey / JavaScriptCore）是否一致 |

**同机一致是最低门槛，不是验收。** 它若不过，项目当场就要换物理库；它过了，只说明可以继续验下一层。

**`U-025` 因此从 `open` 进入 `testing`，不能关闭。**

## 4. 一个额外发现：f32 对确定性的双面影响

Rapier 是 f32 这件事，goals.md 与 adr-001 都没写过。它有两面：

- **有利**：f32 精度低，意味着**小于 `2.4e-7` 的差异会被直接吸收**，不会被放大成分叉。
  这给跨平台一致留了一点缓冲。
- **不利**：f32 的中间运算更容易受**指令集差异**影响（FMA 融合乘加、SIMD 宽度、
  x87 与 SSE 的舍入差异）。而这些差异**大于** f32 epsilon，会被放大。

结论：**这一轮的通过完全不能外推到跨平台。** 反而说明跨平台那一轮必须真的在
不同架构上跑，不能靠"同机通过所以应该没问题"推断。
